# Release notes: 6.2.0

All eleven artifacts are at `6.2.0`, aligned ([VERSION_MATRIX.md](VERSION_MATRIX.md)). This release is the field findings program ([docs/specs/FIELD_FINDINGS.md](specs/FIELD_FINDINGS.md)), a Loom tutorial and a starter set. Each item says what changed for you.

## Starting workflows and supervising them (phase 33, Loom)

- **`start`, `wait`, `cancel`, `steer` and `supervise <handle>`.** A script can start a workflow as a child run of its own, get a handle at once, and then wait for it, cancel it, steer it and watch it with rules, so one workflow runs, watches and operates others. A child has its own journal, a budget that is also charged to its parent, a deterministic run id (a restart finds the same child and never repeats an effect), and a status the script reads as a value. `call` is unchanged. See [the guide section](../src/loom/ai-agent4j-loom/LOOM_GUIDE.md#starting-workflows-and-supervising-them-start-wait-cancel-steer-supervise) and the [design](specs/33-async-workflows/DESIGN.md).
- **`supervise` rules.** Counted rules (`tokens`, `cost`, `calls`, `elapsed`, `idle`), assertions in code (`never calls`, which refuses the call before it runs, `calls ... at most`, `calls A before B`, `reaches ... within`) and judged assertions (facts only unless `seeing content`, one-word verdicts journaled so a restart never asks again, paid from the block's own budget).
- **Bounded.** `max_children` and `max_depth` with host ceilings, a required budget on every `start`, a reservation that refuses a `start` the parent cannot pay for, a required timeout on every `wait`, and a parent that ends cancels its children within a grace period.
- **`weave audit` LA28 and LA29** for a script that can steer a started workflow and for each judged rule; `weave check` has errors and warnings for a missing budget or timeout, a handle written into text or given to a tool, an agent that is not steerable, an unbounded start in a loop and more.
- **For hosts.** `LoomHost` keeps a child as a sibling run whose record names its parent (`RunRecord.parentRunId`; a JDBC table made before this release gains a nullable column), with `LoomHost.Builder.childLimits`. See [API compatibility](API_COMPATIBILITY.md).
- **Not in this release yet:** `weave run` does not start children (it has no place to keep their runs), the graph, `timeline`, Fabric and the live page, the VS Code extension and the compatibility kit do not show children yet, `start ... timeout` is not enforced and `cancel ... rewind` is refused ([VERIFICATION.md](specs/33-async-workflows/VERIFICATION.md) lists what is built and what is not).

## A2A in Loom: calling and being called (phases 32c to 32f)

- **`remote`, `agent_channel`, `ask` and `expose`.** A Loom script can call an agent another organisation runs with a plain `delegate`, say who answers its questions, ask a channel a question of its own, and let other agents call one of its workflows. What comes back is untrusted; a send is never repeated by a crash; a call that cannot finish suspends the run and holds no thread. llm4j runs no server, no poller and no authentication: the host supplies the transport, the channels and the endpoint. See [the A2A pages](a2a/README.md).
- **`weave card`** prints the agent card an `expose` block shows to outsiders, with no network and no model, so a reviewer sees in a diff what a change does to what the world can see.
- **`LoomTaskRunner`, `RemoteTasks` and `ExposedCard`** (in `io.github.llm4j.loom.host`) serve an `expose` block as A2A tasks over a `LoomHost`, carry a run on when a remote task changes, and build the card.
- **`weave audit` LA24 to LA27 and a wider LR02.** An exposed workflow counts as reading untrusted content (LA24), a call to a remote is a place data leaves (LA25), an `audience: automatic` channel answers with no person (LA26), and an exposed workflow with no spend cap is high (LA27). The reliability rule LR02 now counts a call to a remote as able to act.
- **Watching and testing it.** A remote call is one `loom.remote` span with a `Remote agent failed` incident, a run that outsiders started is marked served so the trifecta signal counts its input as untrusted, `weave test` scripts remotes and channels in virtual time, and the graph, symbols, debugger, narration and cost estimate know the new constructs.
- **The editor and the kit.** VS Code extension 1.4.0 (highlighting, hover and snippets for the new words), compatibility scenarios `a2a_call` and `a2a_expose`, and a compile-only starter, `src/examples/a2a-starter`, for the code around llm4j that you provide.
- **Checked against code we did not write, once.** Mostly against llm4j's own mock agent (its messages are validated against the official protocol definition), and then on loopback over JSON-RPC against the Python SDK's helloworld agent and the A2A project's compatibility kit. That second check found three gaps in llm4j's server half, now fixed: an operation the agent does not offer answers with its own error, an error answers the right request id (`A2AJsonRpc10.idOf`), and the `A2A-Version` a client asks for is checked (`A2AJsonRpc10.requireSupportedVersion`). Not checked: gRPC and REST, streaming, push notifications, any other SDK.

## A2A: serving an agent from Java (phase 32b)

- **`A2AHandler` lets others call your agent, from any web stack.** You authenticate the caller and pass a scope key; the handler applies the specification's request rules, shows a task only to the scope that created it, never blocks (a send that must wait returns a stage the host completes), and starts nothing. `AgentCardBuilder` makes the card (no streaming, push or extended card unless you say so). `AgentTaskRunner` exposes a plain `ReActAgent` with a per-task agent function, your `TaskStore` and your `Executor`, and refuses to start until you confirm the agents have limits. See [docs/a2a](a2a/JAVA_GUIDE.md).

## A2A: calling a remote agent from Java (phase 32a)

- **`RemoteAgent` calls an agent that someone else runs over the A2A 1.0 protocol.** It checks the card, refuses a card that points at a host you did not declare, offers no supported endpoint, carries a failed signature or requires an extension your transport lacks, and makes one call per operation. It never waits or polls. llm4j runs no server and ships no HTTP client: you implement `A2ATransport` and `AgentChannel`; `A2AJsonRpc10` translates A2A 1.0 over JSON-RPC. Questions, authorization requests and files go through your channel inside limits the runtime enforces, and received files are written safely under `received/` in your media root. Start at [docs/a2a](a2a/README.md). The Loom support (`remote`, `expose`, `agent_channel`, `ask`) and serving an agent come later in phase 32.

## Two new skills, and a lighter workflow-guide skill

- **`llm4j-workflow-patterns`** picks the shape of a workflow from what the person wants to build (eleven patterns) and starts from a tested skeleton: each one is a starter's `main.loom`, compared by a test.
- **`llm4j-run-debugging`** finds out why a run went wrong, from its journal and with no keys (`weave why`, `whatif`, `step`, `timeline`, `rewind`, `capture`), and fixes it with a test that keeps it fixed.
- **`llm4j-workflow-guide` is about half the size** (`SKILL.md` went from 9,500 to about 5,000 words): every rule is in short form with a pointer to its full text in the new `references/guiding-rules.md`, which is installed with the skill. It gains a **fast lane** for a quick first version that skips evidence, never safety, and says what was skipped, and it now mentions prompt caching.
- `weave guide --install-skill` installs six skills; `--skill patterns` and `--skill debug` install the new ones, and `make skill-package` builds their zips.

## Media in Loom (phase 31e)

- **`attach` sends a picture, recording, video or PDF with a task.** `delegate "What is the total?" to Vision attach image "{receipt}" -> total` (also `broadcast`, `handoff` and `human_prompt`); `extract Receipt from image "{receipt}" -> fields` for an extractor. Files are read only from the folder named by `media_root: "./assets"` (no `media_root`, no files), with `media { max_bytes: 20MB  max_items: 4 }` for limits. `intentclassify` takes no media. **Visible changes:** none for a script that does not use them; `attach`, `media_root`, `media` and `unscanned` are keywords only in the places above, so agents and variables with those names still load. The Loom guide has a section on it: [LOOM_GUIDE.md](../src/loom/ai-agent4j-loom/LOOM_GUIDE.md).
- **`weave check` catches the mistakes before a call is paid for.** A kind the agent's model cannot take, a file that is missing, too large or outside `media_root`, a missing `media_root`, or an `attach` on a statement that cannot take it is a load error; a path filled in at run time is checked when the step runs, before the model call.
- **An agent or extractor with `pii: mask` or `pii: block` refuses media** unless it says `guard { pii: mask  media: unscanned }` (extractor: `media: unscanned`), because masking cannot see inside a picture or a recording.
- **Replay is safe.** The journal records each attachment's kind, type, size and SHA-256, never the bytes; a resumed or rewound run reloads the file and fails the step if it has changed.
- **`weave audit` rule LA23** fires when the file's name is filled in at run time ([weave-audit.md](security/weave-audit.md)). The graph shows an `attaches` badge on the step.
- **Not yet:** the Fabric run page and the editor do not display the attached media; a media folder outside the script's folder is not allowed.

## Media with agents, masking, budgets and compaction (phase 31d)

- **`agent.run("What colour is it?", List.of(photo))`.** The media goes with the first user message of the run and stays there for every later call; compaction keeps that message. A model that cannot take it is never called. **Visible changes:** (1) `MaskingLLMClient` **refuses a request that carries media** unless you call `allowUnscannedMedia()`, because masking works on text and cannot see personal data in a photo or a recording; text is unchanged. (2) Budgets and context windows now count media (about 1,600 tokens a picture, more for documents, sound and video by size; the provider's reported usage replaces the estimate), so a token budget that was blind to media can now refuse a request that carries some. (3) When compaction removes messages that carried media, the marker or summary now says which ("including 2 images that can no longer be seen"); text-only conversations are unchanged. (4) `run(question, null)` with a bare `null` no longer compiles (two overloads fit); write `run(question)`. The Loom `guard { media: unscanned }` spelling comes with the `attach` clause in 31e.

## Media in a message (phase 31b and 31c)

- **Pictures, PDFs, sound and video now reach the model (31c).** Anthropic takes pictures and PDFs; Gemini takes all four; OpenAI chat takes pictures and PDFs on its current models and sound on `gpt-audio` models; the Responses API takes pictures and PDFs; xAI takes pictures; Ollama vision models take pictures (documented, not yet tried against a running server), as do Kimi and Qwen vision models. Each was checked against the real API on 2026-11-06 except the last three, and `-Plive` keeps them checked (`LiveMediaTest`, and `LiveCachingTest` for the prompt cache). What a model takes is recorded by name; **a model nobody recorded takes nothing**, so a request with media to a new model is refused until it is added. Every provider refuses what it cannot send before any call, even when called directly. See [Media input](../src/ai-agent4j/wiki/Media-Input.md).
- **A `Message` can carry images, sound, video and PDFs, bounded and checked (31b).** `Media.image(path, MediaPolicy.defaults())` (and `audio`, `video`, `document`, or `Media.of` for bytes) reads the file, decides what it is from its bytes (never from its name or label), and refuses an empty or oversize file, a format it does not know, SVG, a kind that is not what the bytes are, and anything the policy does not allow (default: 20 MiB per item, 4 per message, 32 MiB per request). A `Media` prints only its type, size and a short hash, and JSON carries a descriptor (kind, type, size, SHA-256, name), never the bytes. `Message.user("What is the total?", List.of(photo))` attaches it; only a user message can carry media. `LLMRequest` refuses media over the policy. **Visible change:** none for text. A request that carries media the model cannot take is refused before any call with `<provider> <model> does not accept video; accepted: image, document`, so media is never silently dropped. Spec: [docs/specs/31-multimodal-input](specs/31-multimodal-input/DESIGN.md).

## Prompt caching (phase 31a)

- **Anthropic prompt caching, and a bill that shows it.** A request can name the stable parts of itself (`LLMRequest.promptCache(PromptCache.builder().system().tools().throughMessage(i).build())`); Anthropic writes its `cache_control` markers there, up to its limit of four. `ReActAgent` asks for the system prompt and tools on every call and the conversation so far from the second call on; `ReActAgent.builder().promptCaching(false)` and the Loom agent setting `cache: false` turn it off. **Visible change:** a looping agent on Anthropic now pays the cache-write premium once and reads the repeated prompt at a fraction of the price, so its cost falls on runs of more than one call and rises slightly on a single-call agent (set `cache: false` there). OpenAI and Gemini cache by themselves and are unchanged. Every provider reports the cached part of the prompt as `usage.cached_tokens` (Gemini newly), Anthropic also `usage.cache_write_tokens`. A price table can now give a model's cache read and write rates (`model = in / out / searches / cache read / cache write`), and budgets and cost reports price cached tokens at them; a model without cache rates is priced as before. Spring properties do not yet take cache rates. Spec: [docs/specs/31-multimodal-input](specs/31-multimodal-input/DESIGN.md).

## The engineering discipline program (phases 24 to 29, in progress)

- **Extractors (phase 24a).** A new internal node, `extractor` / `extract X from text -> var`, pulls typed fields out of text with no transcript, no shared prompt and no tools. An optional field the text does not state is `missing`; a required one is never invented and fails the step at once. It is journaled, budgeted, traced by field names only, drawn in the graph, scriptable in `weave test`, mocked in `weave eval --mock`, asserted in eval4j (`runsExtractTimes`, `extractedField`, `leftMissing`) and listed as its own cost line. Existing scripts are unaffected.
- **Who sees what was said before (phase 24b).** An agent can leave the run's transcript with `memory { transcript: none | own | all }` and the shared prompt with `shared_prompt: none`. The default stays `all`; `weave explain` and the graph now say, for every agent, what it sees ("sees everything said before it"), so the default is visible. New low review rule LP08 (an agent that sees no transcript is given a task that passes no variable).
- **Agents used as extractors, and the transcript as a security path (phase 24c).** New medium review rule LP09 notices an agent that only pulls fields out of text and offers `weave review --fix-finding <id> --option to-extractor` (needs `--yes`; `--dry-run` shows the diff). New audit rule LA21: an agent that receives the whole transcript after an agent that reads untrusted content has run is treated as reading untrusted content; **it can make LA01 fire for an agent that did not have it before**, so a CI job with `weave audit --fail-on high` may start failing for a real trifecta it was missing. Fix: `transcript: none` on the receiver. **Visible change:** `weave explain` lines for agents end with the new "sees …" phrase, and the graph JSON agents carry `transcript`.

- **Reason, then extract (phase 25a).** New medium review rule LP10: an agent that has to think (tools, web search, rounds, or a long prompt) and must answer in a large schema (a nested object, a list of objects, or more than 5 fields). It points to the way out: let the agent write prose and add an extractor. LR05 and LP02 now offer a classifier, an extractor or a small schema, in that order. `weave review --fail-on medium` in CI may start failing; `LP10 = off` or an acceptance with a reason restores it. New settings `prompts.large-schema-fields` (default 5) and `prompts.short-prompt-tokens` (default 300). **`weave review --fix-finding <id> --option split`** rewrites the agent into prose plus an extractor (needs `--yes`; never edits tests). **Bounded fan-out (25e):** `for each … max N` (and `parallel for each`) with `on_too_many { … }`. A list longer than `N` fails the workflow before any item starts and names the agent or extractor that wrote it; `on_too_many` runs instead with `_count` and `_max`. New trace event `fanout_exceeded` (counts and names, never an item), a *plan over its bound* incident on the live page and in Fabric, `weave capture` turns the failed run into a test, new medium review rule LR13 (`for each` over a model-written list with no `max`), and the cost estimate calls the worst case of such a step *unknown*. `weave generate` is told to bound such lists; two recorded generator transcripts were hand-edited to add `max`. Starter 06 gained `max 4`. **Starter 16 (25d)** shows a long agent whose progress is a typed, journaled variable the script owns: a bounded loop, a worker with no transcript and an extractor that records progress. **Examples (25c):** in `getviral`, Researcher and Strategist now think in prose and an extractor follows; six agents in `getviral` and `nirmaan-yantra` keep a schema on purpose, with the reason in each example README.
- **Evaluation is loud, and the dataset is the requirements (phase 28a).** The Testability lens is on by default (`lenses = -testability` restores the old default), so **review output grows for most projects** (LT01 and LT06 now speak); `weave review --baseline write` records what exists. **LT06** is now exact and uses the same dataset lookup as `weave eval`: one finding per script naming every agent, extractor and evaluator without a golden case (a workflow case that names an agent in an `expect` line covers it), medium when the script can write, send or ask a person, else low; it no longer needs `heuristics = on`. A script with no golden cases at all prints `No evaluation: nothing has measured whether these agents are right. weave eval --init starts one.` after `weave run` (on the error stream; `--quiet` hides it) and `weave deploy` (the generated README gains "Before you rely on this"), the live run page shows a dismissible banner (the run start event carries `evaluated: false`), and `weave next` lists "Requirements (golden dataset)". When the README says `Evaluation: skipped`, the notice says so instead. `weave guide` stage 2 is "Write the requirements as a golden dataset"; skipping stays possible and recorded. Every starter now carries its requirements as `eval/golden/workflow.yaml`.
- **The gate: no extractor or evaluator without golden cases (phase 28b).** `weave check` (and `weave eval --check`, `weave serve`, `weave deploy`) now **fails** when a script uses an `extractor` with no case that names fields, or an `evaluator` without a case that breaks, and one that is clean, for every rule of every policy it checks. Cases live in `eval/golden/<node>.yaml` (extractors: `input`, `expected_fields`, `expected_missing`; evaluators: `policy`, `text`, `expected: { rule: violated | clean }`, `near_miss`). The cases' structure is checked too; their quality is not. There is no flag to skip it. `weave eval <script> --init` writes the files with comments and no cases, and a scaffold never satisfies the gate. **Visible change:** a project that already uses an extractor or an evaluator (both are new in this release) fails `weave check` until it has cases; starters 08, 16 and 17 now carry theirs. Loading a script in a Java host never reads `eval/golden`; it logs once at WARNING that the gate is a build-time check. The LP09 `to-extractor` and LP10 `split` fixes now say which file to write. Not yet: `weave eval` running these cases against a model (the false-alarm rate is 28c/28d).
- **`weave eval --requirements`: the dataset as a page a person can sign off (phase 28c).** Renders the golden dataset as plain sentences, with no model and no key: what each workflow, agent and node must do and must never do, each policy rule with the examples that break it and the near misses, the identity of what was read (dataset version and hash, each policy's version and hash) and what has no requirement yet; personal data in a case is masked. `--format html` writes a page to share. `--requirements --approve --approver <name> --why "<text>"` records the exact identity in `eval/requirements-approvals.yaml`, and a later change to any case or policy makes the page say it changed since. `--approver` and `--why` now also serve `--approve`.
- **`weave eval --changed`, evaluator false-alarm rate, a CI file (phase 28d).** Every complete real `weave eval` records a fingerprint per agent and node (prompt with the shared prompt, model, temperature, schema or fields, tools and their effect, an evaluator's policies by version and hash, the node's own cases) in `eval/last-run-fingerprints.json`; `--save-baseline` records them in `eval/baseline-fingerprints.json`. `weave eval --changed [--since baseline|last|<file>]` runs only the cases of the nodes that differ, plus every workflow that reaches one, prints *what changed* first, needs a cap, and counts anything it cannot read, or has no reference for, as changed. `weave eval` now also runs the cases of extractors (exact field checks, no judge) and evaluators (per rule) and reports an evaluator's **false-alarm rate** (clean and near-miss answers flagged violated or unsure, with a 95% interval): above its `false_alarm_limit` (10%; `evaluator E { model: "…" false_alarm_limit: 5% }`) the run **fails**. The report's section is now **By agent and node**. `weave init` writes `.github/workflows/weave.yml`: free checks on every push, `weave eval --changed` with a token cap on pull requests when a key is configured (skipped with a notice otherwise), and a full scheduled run written but commented out. **Visible change:** the report section is renamed ("By agent" to "By agent and node"); a project that uses an evaluator can now fail `weave eval` for being timid. A mock run leaves node cases unjudged and claims no rate.
- **Architecture you can review (phase 29).** A new page, [docs/REVIEWABLE_ARCHITECTURE.md](REVIEWABLE_ARCHITECTURE.md), states the idea behind the guarantees (Loom is a language, so a workflow's architecture can be reviewed by people and checked by tools) and shows thirteen mistakes with the script, the exact `weave` output (generated by a test) and the fix. Nine new probes, P9 to P17 in [probes/README.md](../probes/README.md), ran the same scenarios on Loom, LangGraph 1.2.18, LangChain 1.4.7 and the Python Google ADK 2.13.0 with fake models; every statement about another framework links one. `WHY_LLM4J.md` gained a row per mistake; the README, wiki, stack pages, tutorial README, `llms.txt`, the extension README and the workflow-guide skill carry the claim. Documentation only: no behaviour changes.
- **A different model judges by default; LR12 and LR14 (phase 28e).** `weave eval` no longer grades an agent with its own model unless you say so. The judge is `--judge <model>`, else `judge:` in `dataset.yaml`, else `judge = <model>` in a project-root `eval.properties`, else the cheapest other model the project can reach (another provider when there is one; the ranking is a rule of thumb from the model name, so name the judge when it matters). *Read this first* says which was chosen and why; `--judge same` judges a model with itself on purpose and *Cautions* says scores may be biased; with only one reachable model it judges itself with that caution and never refuses. **Visible change:** a project that relied on the agent grading itself now needs a second reachable model or `--judge same`, and its scores can move. New review rules **LR12** (medium: a loop whose condition reads the answer of an agent that also produces the work the loop iterates on) and **LR14** (low: a `check` whose evaluator runs on the same model as the agent that wrote the text; the design had both as LR12, but a rule is about one kind of step). Starter 17's evaluator now runs on a stronger model than the agent it checks. Not built: LR12 on a `rewind ... when` condition and its `add-reviewer` fix. The confidence-is-not-calibration note is in the Loom guide and two skills.
- **Routing within limits (phase 27e).** The agent a `delegate` is sent to can still come from data, but a model's words can no longer pick any agent. Write the allowed names on the step, `delegate "…" to {task.owner} in [Researcher, Writer] -> results[task.name]`, or take the value from a field typed `enum[...]`. A value outside the list is **refused**: the step does not run, the trace records `route_refused` (names the agent that wrote the value, never its text) and `on_failure` handles it like any failed step. `weave check` verifies every name in an allow-list is a declared agent, and a target nothing bounds is an **error** when any agent holds a tool that changes things or reaches private data, and a warning otherwise. New audit rule **LA22** reports the same. **Result names:** `-> results[task.name]` stores each answer under a key in one variable (a plain word only; a parallel `for each` is safe). A bare `-> {task.name}` still works for a new, plain name that the script does not use elsewhere and is refused otherwise, with a message that points at the map form. **Visible change:** a script that routes with `to {x.owner}` and no list or enum now warns, or fails to load when an agent holds a changing tool; a loop that wrote the same dynamic name each round now stops with the message above. Starter 06, the tutorial chapter 4 and `getviral` were moved to the new form. The lint that warns about a variable set and never read now reads `results[key]` as the variable `results`. Not built: the `to-boundary` fix, which would add the list for you.
- **Review: human oversight on by default, LH05, LH06, LR11, and LA02 offers the boundary (phase 27c).** The Human oversight lens (LH01 to LH06) is now one of the default lenses; `lenses = -oversight` in `review.properties` restores the old default. **Review output grows for most existing projects** (LH03's question count, LH01 and LH04 now speak): record what exists with `--baseline write`. New: **LH05** (medium) an agent's `approve:` covers a tool that changes things in a workflow with a `schedule`; **LH06** (low) the step form of LH02: `use ... approve` on a tool that only reads (LH02 keeps the agent form); **LR11** (medium) text an agent wrote freely reaches a step that changes something (a `delegate` to an agent holding a changing tool not under `approve:`, or a `use` of one without `approve`) with no extract, classify, task, check or decide between. `weave audit` rule LA02's advice now offers the boundary first. Not yet: grouped findings and the one-time baseline suggestion (R9), LH03 counting steps' approvals, LH02 for `run ... approve`, the `to-boundary`, `insert-extract` and `approve-step` fixes.
- **`use Tool(...)` and `approve` on a step (phase 27b).** A script can call a tool with no model in between: `use Notify(text = draft) -> receipt retry 1 timeout 30s on_failure { ... }`. It is the same tool object, reach checks, secrets and journal as an agent's call, arguments are matched against the tool's parameters (an unknown or missing one fails the step and names what the tool takes), the result is journaled so a resumed run does not call twice, `weave check` refuses `retry` on a changing tool that is not safe to repeat, and under a policy it is an exit. `approve ["heading"]` (on `use` and on `run`) asks a person once, showing the exact arguments with personal data masked; a no runs `on_declined { ... }` (only valid with `approve`) and is not a failure; anything but a yes is a no; a resumed run never asks twice. New graph node kind `use`, trace field `by: use` on `tool_call`, eval4j `usesTool(name, times)`, CTK scenarios `use_tool` and `approve_step`. Not yet: the review changes (LA02, LH02, LH03, LH05), the oversight lens by default, starter 07 rewritten, and checking a `use` argument's names at `weave check` (it is checked when the step runs).
- **Every tool has an effect (phase 27a).** A tool says what it does to the world in the three words a task uses: `effect: none | reads | changes`, and an `openapi` tool or an `mcp` server declares each operation with `effects: { listOrders: reads, createRefund: changes }`. Your word is final for the runtime, `weave check`, `weave audit` and `weave review`. With nothing declared, Loom assumes an effect from the kind of tool (the table is in `LOOM_GUIDE.md`) and says so: `weave explain` prints `Tool X: changes (assumed; say what it does with effect: …)` and `weave review --format json` carries `effect`, `effectSource` (`declared` or `assumed`) and `effectReason`. **Visible change:** a tool you declare `effect: reads` (a `POST` search, a Java tool) no longer counts as needing approval in `weave audit`, so LA02 and the unapproved-effects list shrink; a tool you leave undeclared behaves as before. `reach:` on a `class` tool keeps working; `effect:` with `reach:` on one tool is an error. An MCP server's `readOnlyHint` is used where it has been read (`McpEffects`); the audit does not connect to a server, so an undeclared MCP tool is still assumed to change.
- **Policies, evaluators and `check … against` (phase 26a and 26b).** Rules about what must never be said live in their own markdown files under `policies/` (`## rule_id`, then what breaking it looks like), versioned like prompts, never put into a prompt. `evaluator Name { model: … samples: 3 unsure below 0.8 fallback: [...] }` is a new stateless node that judges a text against the rules and fails closed (`unsure` blocks, counted apart). `policy HouseRules: "house-rules" checked by Compliance` declares a policy. `check reply against HouseRules using Compliance -> verdict on_violation { rewrite with Editor | ask person | replace with "…" | fail } on_unavailable { … }` judges at the edge; a rewrite is stateless and checked once more, `ask person` accepts `send as is`, `send this instead: …` or `stop`. New trace event `policy_check` (rule ids, versions, hashes, action; never the text or a reason), audit events `policy_violation` and `policy_override`, graph node kind `check`. `weave check` rejects a missing or empty policy file, a duplicate rule id, an unknown evaluator or policy, and warns that `unsure below` needs `samples: 3`. A script that declares none of this behaves as before. **The runtime guards the exits (26c).** With a policy declared, model-written text cannot leave the workflow unchecked: the `return` of a run, the arguments of a task that changes things, and an agent's own calls to a tool that changes things are refused (the last are checked automatically by the evaluator each policy names with `checked by`, before approval). Where a value came from is kept beside the values; a value with no record counts as unchecked. `weave check` follows model text to the return and names both lines. New trace events `sink_blocked` and `tool_refused_by_policy`. **Visible change:** a script that declares a policy and returns an agent's reply without a `check` no longer loads; a script with no policy is unchanged. **Leak guard (26d):** `guard { prompt_leak: warn|block|off  internal_refs: [..] }` catches an answer that repeats its prompt, the shared prompt or a policy rule, or names an internal reference; `warn` by default under a policy. **Review rule LY07** (medium, once per script): model-written text leaves a scheduled or acting workflow and no policy is declared. **Testing:** `weave test` scripts an evaluator per rule (`evaluators:`), asserts `checks:` and `actions:`; eval4j gains `checksPolicy`, `violated` and `actionTaken`; a free mock run answers every rule "no" and says it did not judge. **Starter 17** shows the whole boundary. The `shared_prompt` example and preflight C4's advice no longer teach putting a rule in a prompt. Not built: the cost lines and budget reserve for checks, the live-page incidents for checks, the `add-policy` fix, and the calibrated evaluator backend.

## Fixed: answers are no longer cut short without a word

- **No more silent 1,024-token limit.** With a token or cost budget and no `per_call`, every model call was capped at 1,024 output tokens (`BudgetSet.DEFAULT_OUTPUT`), so long answers ended mid-sentence while the run
  reported success. The limit is now 8,192 tokens (`BudgetSet.UNSPECIFIED_HOLD`), or the model's known maximum from the seeded model list when that is smaller, bounded by what the budget still affords. What is sent is what is held, so one call cannot spend more than was reserved. An agent that needs longer answers sets `per_call`, which is held in full. **Behaviour change:** answers that were clipped
  become whole, so token use rises to what the agent really writes, still inside the budget. A script that relied on the clipping to save cost should set `per_call`. Parallel branches are not starved, because each holds at most 8,192.
- **A cut answer is named.** When a provider stops an answer at its limit, the run prints `✂ N answers were cut at the output limit: Writer (2)`. The count was already in the trace as `truncated`.
- **`weave explain` states each agent's output limit** and where it comes from (its `per_call`, the model's maximum when that is under 8,192, or the default).
- **A cost that is an estimate says so.** The spend table marks estimated rows `~$` and names the agents whose provider reported no usage, instead of the generic note.
- **Gemini grounding with `recency:` works again on clocks with sub-second precision.** The times sent are whole seconds. (Verified by a unit test; a recorded request from the real API is still owed.)

## `weave eval`: a report that always has the same shape, and a by-agent view

- **The report has nine fixed sections** (*Read this first*, *Overall*, **By agent and node**, *By dimension*, *By slice*, *Cases*, *Cost*, *Cautions*, *How to reproduce*) in the terminal, in `--report` and in `--json` (`sections`). A section with nothing to show says why instead of disappearing. Tests pin the structure.
- **A by-agent view, for every run, with no tag or setting.** Each agent that took part gets a row built from the run: its pass rate on the cases aimed at it (with a 95% interval), calls, tokens, cost, answers cut at the output limit, steps that used a fallback, and its worst outputs with the judge's reason. (Before, the dashboard's By-agent table needed `agent:` tags written by hand and `weave eval` did not feed the dashboard at all.)
- **Outputs are kept and shown.** *Cases* shows each case's input, the output that was judged and every line's verdict with its reason. The output of a case that fails an `expected_output_not_contains` check is withheld, so a report never repeats what the case guards against (a card number, a secret).
- **The judge's cost is in the cost,** shown beside the agents' and the total, with the cost per passing case. Without `--prices` the figure is `unknown`, not zero.
- **`weave eval` writes the dashboard bundle** (`target/eval4j/runs/<id>/` or `eval-runs/runs/<id>/`): all cases, their outputs and verdicts, and a case per agent for the By-agent table. Render it with the `eval4j-report` command line.
- **A rubric line can name its dimension** (`{ text: ..., dimension: tone }`), counted under that dimension only; plain lines still count under every dimension of their case, and the report says how many do.
- **`--repetitions N`, `--judge-samples N`.** The report gives pass@1 beside pass^N and consistency, names unstable cases, and states its resolution (how small a change this many cases can tell). A line whose judge samples disagree widely is left unjudged.
- **A sealed held-out set.** Cases tagged `split:heldout` run only with `--release-gate`, which the report records; the generalisation gap (validation minus held-out) is reported and warned about above 10 points.
- **Datasets and baselines that cannot slide.** The report names the dataset's identity (declared `version:` plus a hash of its cases). `--save-baseline` needs an approver and a reason and never replaces an earlier baseline; `--baseline` compares with the current and the previous baseline and lists regressions; a different dataset is refused unless `--allow-version-change "<why>"`.
- **A workflow's output is defined** (its `return`, else the last agent's answer, else its last `note`) and an empty one is an error case; it is no longer sent to a judge.

- **`weave doctor` names two Loom jars that share a version but are different builds** (the running one, copies in `~/.m2`, the editor extension's bundled jar, `WEAVE_JAR`) in one sentence with the fix, and says nothing

- **The inspect and Fabric add-ons refuse a mismatched core in one sentence.** `loom-inspect` checks at start-up that it is the same build as the `ai-agent4j-loom` it runs against; `loom-fabric` does the same against the
  inspect core it bundles. A development build must match by commit; two releases match by version. Before, the mismatch showed up later as a missing class.
- **The skills install complete.** The deployer skill's scripts look for each jar in one order (the variable, the editor extension's jar, `bin/`, `~/.llm4j/tools/<version>/`, a build), the same in the shell and PowerShell versions, and newest first. `weave guide --install-skill` ends with what was found and what is missing (`weave tools fetch fabric` for a missing Fabric jar) and never says the scripts are ready when one would stop. New: **`weave tools fetch fabric|inspect|all`** downloads the jars for this weave's version from Maven Central after listing them and asking (`--yes` skips the question), keeps a file only if its published SHA-256 (or, where Central offers only that, SHA-1) matches, writes only under `~/.llm4j/tools/<version>/`, refuses a development build, and never runs what it downloads.
- **`weave` for a coding agent in a plain terminal.** The workflow skill ships `scripts/weave` (and `weave.cmd`): it finds a weave or prints the one install line. `weave doctor` says when `weave` is not on this terminal's PATH, what the editor extension's PATH entry covers (VS Code's own terminals only) and what to do.
- **The editor offers the coding-agent set-up once** (extension 1.2.0): a notification when a folder with a `.loom` file has none; it writes nothing until you choose.
- **Keys in a template file are caught more precisely, and moving them is one command.** `weave check` (and `doctor`, `next`) now watch `.env.example` and any `*.example`, `*.sample` or `*.template` file in the project root, and flag only names that hold a secret (ending in `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, and so on): `PORT=8080` or `LOG_LEVEL=debug` no longer raise it. The warning names the file and the name, never the value, a prefix or its length, and gives the way out: `weave secrets import-env --from <file> --secrets <store>`. **New:** `import-env --from <file>` reads `NAME=value` lines from a file (every secret-named value, or just the names you list), stores them encrypted, and for a template offers to blank the imported values afterwards (`--blank` does it without asking); a real `.env` is never changed. Every starter's `.env.example` now says not to put a key in it and shows the store as the encrypted alternative.
- **A jar with a half-compiled class cannot be released.** `make release-check` and the CI release job run `scripts/CheckJars.java`, which refuses a jar holding an editor's `Unresolved compilation problem` stub or lacking its
  identity; `scripts/verify-vsix.sh` does the same for the jar the extension bundles; `scripts/doctor.sh` warns when `target/classes` holds a stub. See CONTRIBUTING.md.

## Sources: a missing set is now said, not skipped

- **A grounded agent that returns no sources is named.** When a grounded agent's answer comes back without any sources (the model did not search), the run prints `⚠ Grounded but no sources came back: Researcher (1)`.
  Before, `{research_citations}` was simply not set and a script's own fallback hid it. Checked against the answer recorded from the real Gemini API: sources do reach the workflow from a plain delegate, from inside
  `parallel` and from a step with `expecting`, so the field report's "citations never arrived" is explained by the model not searching, not by the workflow dropping them (the cause there is still unconfirmed).
- **`weave check` warns when a script reads `{x_citations}` for an agent that is not grounded**, since that variable can never be set.

## Fixed: a run that fell back says so, and what it returned is shown

- **A degraded run is named.** A run that finished by using `on_failure` fallbacks prints `⚠ Degraded: Researcher, Editor took their fallback (2 of 5 model steps)`. The exit code stays `0` (no existing script
  changes meaning); `weave run --exit-degraded` exits `7`. **Behaviour change:** a run in which *no* model step succeeded (every step fell back) is now a failure, exit `1`, not "completed successfully": it
  ended with a result no model contributed to. `weave test` can assert `degraded:` and `fallbacks:`.
- **`weave run` prints what the workflow returned** under `Result:` (`--quiet` leaves it out). A workflow that returns nothing says so. Scripts that parse `weave run`'s output should use `--quiet`.
- **`weave eval` never judges an empty output.** A workflow or agent with nothing to judge is an `ERROR` case with the reason, no judge call is spent on it, and the evaluation exits non-zero. A workflow's output
  is its `return`; else (as before) the answer of the last agent it asked; else its last `note`.

## Fixed: what a script declares now reaches the run

- **`shared_prompt` is applied.** In 6.1.0 and earlier no `weave` command (`run`, `eval`, `test`, `serve`) told the agents the shared prompt, in either form (`shared_prompt: "text"` or
  `shared_prompt: prompt "house-rules"`). It is now put first in every agent's system text. If your workflow relied on rules in the shared prompt, they were not in force before; check a run's behaviour
  after upgrading. See the correction in [RELEASE_NOTES_6_1_0.md](RELEASE_NOTES_6_1_0.md).
- **`weave check` no longer calls a named shared prompt file "not used by any agent".** It was the same fault.
- **`supervise` and `intervention` blocks are applied.** A script's own `supervise Agent { ... }` rules and `intervention { ... }` defaults were dropped when the script was loaded, so a supervised workflow ran
  unsupervised and `weave explain` did not list them. They now apply, including `supervise` blocks in imported files. An imported file's `shared_prompt` is not imposed on the file that imports it.

## New: `weave preflight`, one real answer before you spend more

- **`weave preflight script.loom`** asks each agent one real, capped question and checks what a run needs: the key works (C1), the model accepts the request (C2), the answer is whole, not cut or empty (C3), the shared prompt reaches the model (C4, with a random canary kept in memory only), grounded agents return sources (C5), the price and context window are known (C6) and the budget is sensible (C7). It asks before spending unless `--yes` or `--mock`, stops at `--max-tokens` / `--max-cost`, and exits `0` (pass or warnings), `1` (a failing check) or `3` (stopped by the cap). `--format json` is for scripts. It writes `.loom/preflight.json`.
- **`weave next` knows the preflight** and offers it before the deploy step (and again when the script changed since or the last one failed). `weave next --format json` lists the steps and the preflight state.
- **`weave next --confirm real-run`** records that a person read one real answer and judged it. After a passing preflight, `weave next` asks for that read before the dataset is built on it; an edited script needs it again.
- **`weave eval --check` says how many drafted cases no person has reviewed.** A case an assistant drafted carries the tag `author:assistant`; the person who accepts or edits it adds `reviewed_by:<name>`.
- **The skills share one `references/conventions.md`** (nine rules: roadmap and checklist, the planner question, co-written datasets, a real answer read early, read-back, tested README commands, keys asked first, selection shares, visible skipping). It is installed with the workflow, deployer and harness-design skills, and a test keeps the three copies identical.
- **`weave next --format json` reports the ten stages of the journey**, each `done`, `failing`, `not-started`, `skipped` or `stale`, read from the project's files and recorded results, and names the one to take now (a failing stage first). `weave eval` now records its last finished run (mock or real, the dataset version and the script) in `.loom/eval.json`, so a real evaluation of an older script shows as `stale` and a mock one does not count. The engine answers the same JSON as `loom/next` ([PROTOCOL.md](serve/PROTOCOL.md)).

## Changed: the graph draws parallel blocks as lanes and groups consecutive `set`s

- **A `parallel` block is a node whose branches are lanes.** In `weave graph` JSON the branches are now nodes with their own lines and `on_failure` handlers, grouped in the block's `attrs.lanes`; in Mermaid each lane is a `subgraph`, and a `parallel` inside a lane nests as a `subgraph` inside it (each node declared once). `weave graph` has two formats, JSON and Mermaid; there is no separate text format, and `weave explain` lists the branches. Steps after the block keep their ids. See [API_COMPATIBILITY.md](API_COMPATIBILITY.md). **A consumer that expected the block to be one node with an edge to the next step now sees the branches in between.**
- **A `set` node carries its `value`** (masked and cut at 200 characters).
- The editor's Flow view and the shared renderer (Fabric, the eval report) draw a fork, one lane per branch with its failure handler under its step, and a join; consecutive `set`s are one small card that opens to list them (`loom.graph.groupSets` turns that off).
- **The graph-render tests had been failing since the `classify` statement was added to the sample script (19 of 73 on a clean checkout), unnoticed because no CI job runs them.** The table now matches the sample; the tests pass (91).

## Changed: strings, hints for known mistakes, and the options of `weave test`

- **A string can hold a double quote and end with a backslash.** `\"` is a double quote and `\\` a backslash inside a string; any other backslash stays as written (`\n` and `\t` are read later, as before). **A string with a doubled backslash (`"C:\\dir"`, `"\\d+"`) now holds one backslash, and a string that ended in `\"` expecting the backslash to be text now reads differently**: none of the scripts in this repository does (a test lists any), but check yours; the lexer says what to write when a string would end in a lone backslash. The editor's parser reads strings the same way.
- **A known mistake says its fix.** `expecting {…}` after `retry N` on a `delegate` is a parse error that names the right order, and a scripted task result with the reserved key `value` says what to write instead. The registry (`KnownMistakes`, see `CONTRIBUTING.md`) is one row and a test per mistake.
- **`weave test` takes `--classes`, `--loot` and `--env-file`**, like `weave run` and `weave eval`. In a built Maven project the three use `target/classes` and say so in one line; `--no-auto-classes` turns that off. (`--loot` is checked to exist and otherwise ignored by `test`, which scripts every tool.)
- **The log is not the answer.** Every command logs at WARNING by default; `-v` (or `--verbose`) shows the progress lines and `-vv` the detail. `weave run`, `resume`, `tick` and `daemon` no longer print Loom's INFO progress lines unless you pass `-v` (or set `WEAVE_LOG=info`); a script that read `INFO:` lines from them must pass `-v`. `weave eval --verbose` works as before.

## Changed: the review separates the machine from the script, the cost block says what it assumed

- **A key that is not set is a setup finding, not a HIGH one.** `weave review` lists it under **Setup** ("about this machine, not a finding in the script"), outside the counts, `--fail-on` and the editor's open-findings number; `--include-setup` counts it as before. The JSON gains a `setup` list and `summary.setup`. The rule: a finding is a script finding only if editing the script can clear it. (A missing prompt file stays a finding.) **A CI job that failed on `--fail-on high` only because no key was set will now pass; add `--include-setup` to keep the old behaviour.**
- **The cost block says what it assumed.** Under the totals, an "Assumed per step" list gives each step's runs and tokens a run, typical and at most, and when the script's token cap is at or below the worst case it says so: "the cap, 150,000 tokens, will stop the run before the worst case, 179,000 tokens: expect cut results". The JSON adds `tokenCap` and `capStopsBeforeWorstCase` per workflow. (Not yet: measured usage from a preflight or a recorded run is not fed into the estimate automatically.)
- **`weave observe rules` works without ceremony.** A missing rules file, or one with only comments, means the defaults apply (it says so and exits 0); a file with rules and no add-on says `weave tools fetch inspect` or `--classes`; `--init` writes a commented starter beside the script and never overwrites.


## New: `substitution: braces`, `real:` tasks in tests, and the parallel fallback pattern

- **`substitution: braces`** (a top-level setting of a script) replaces only `{name}` and `{name.field}`. The default stays `legacy`, where a bare name is replaced too, so no existing script changes meaning; **the next major version makes `braces` the default**, and `LOOM_GUIDE.md` says so. `weave check` now warns about a bare word that is also a variable in every text the runtime fills in (it looked at four statements before; it now looks at all fifteen positions, listed in one place that a test compares with the runtime).
- **`weave check --substitution braces`** previews each text that would change (variable, position); **`--fix-substitution`** shows the rewrite of each bare word meant as a variable as a diff and writes only after a yes (`--yes`).
- **`real: [Task]` in a test case** runs that task's own code instead of a scripted result and still counts it in `expect.calls`. Only a task that declares no effect (`TaskEffect.NONE`) may be real; a task that changes things, or does not say, is refused with the reason. A name in both `real:` and `tasks:` is an error.
- **Parallel branches that fall back** now have a documented pattern with a naming rule (one flag per branch). The language has no new construct for it; whether a condition may read the list of fallbacks is left open.

## New: `weave fabric up | down | status`, one front door for a local Fabric server

- **`weave fabric up`** finds the Fabric jar (`FABRIC_JAR`, then what `weave tools fetch fabric` put in `~/.llm4j/tools/<version>/`, then a build in the checkout), starts it as a separate process, and on the first start writes a generated admin password to `<data>/admin-password.txt` (readable by you only, never printed or put on a command line). A bind beyond this computer is refused without TLS or a proxy. A second `up` changes nothing.
- **`weave fabric status`** shows whether the server runs and, for each client that may report, **when it last reported** (or *never reported*), read from the history Fabric keeps. **`weave fabric down`** stops it, and only ever a process whose command line is Fabric's.
- **The deployer skill's scripts hand over to it** when the `weave` in use has the command (same exit codes) and keep their own logic as the fallback. **A change you can see:** `fabric-up` without a password now generates one instead of refusing; `--generate-password` is still accepted and changes nothing.
- **`run-observed` takes `--secrets-key-file FILE`** (or `LOOM_SECRETS_KEY_FILE`; `-SecretsKeyFile` in PowerShell), so a master key kept elsewhere needs no file named after the store.
- **Fixed: `weave eval` crashed at the end in the standalone `weave` jar.** After the report it writes the dashboard bundle, which loaded a class that names JUnit's abort exception, and the standalone jar carries no JUnit (`NoClassDefFoundError: org/opentest4j/TestAbortedException`). It was found by the skill-package check from an empty folder, not by the unit tests, which have JUnit on their class path. eval4j now loads that exception by name, only when a test is really being stopped (`RunsWithoutJUnitTest` loads the exporter with `org.opentest4j` hidden).

## New: the evaluation design skill, `llm4j-eval-design`

- **A fourth skill designs how a workflow will be evaluated** before the golden dataset is built, and writes it into an `EVAL_DESIGN.md`: eleven stages (readiness, layer map, dimensions, oracles, dataset, harness, run protocol, security, regression and baselines, gates, ownership), a checklist after each, and the nine rules an evaluation lives by. It **asks** the developer and a domain expert and never writes the answer key for a domain fact; anything it drafts is tagged `author:assistant` until a person reviews it. Asked "is my evaluation any good?", it reviews an existing one against the known anti-patterns into an `EVAL_REVIEW.md`, and marks what it cannot confirm from the files as *not verified*.

A mapping page says what the stack does for each decision **today**, and lists each gap with its register id and a workaround; a test checks that every `weave` command and option the pages name exists.
- **`weave guide --install-skill` installs four skills** (`--skill eval` for this one), `make skill-package` builds `dist/llm4j-eval-design.zip`, and `weave next` offers the design when a project has agents and no `EVAL_DESIGN.md` (before the dataset when there is none, or as a review step when there is one; `Evaluation: skipped` in the README silences it).

## New in `weave eval`: answer sets, a validated judge, the cost tail, what the dataset is made of

- **A case may state the answers it accepts** (`correct_conclusion`, `accepted_equivalents`, `rejected`, `acceptable_actions`, `unacceptable_actions`, `required_citations`). The verdict is exact, acceptable, rejected or unmatched; an unmatched answer is unjudged and goes to a person; the report counts the verdicts and warns above a tenth unmatched. Matching is a deterministic key-phrase test; embedding and model matching are not built. Existing datasets read as before.
- **`weave judge validate`** compares a judge with people on a scored reference set (people against each other first, then the judge against their median, with kappa), exits 0, 1 or 2, and records the result so a report can say the judge was validated (and only for that model).
- **The cost section gives the median and p95 cost of a case and the runaway count**, so a few runaway runs show.
- **`weave eval --check` names a thin case class, a slice under ten cases, and the source mix** (from `class:`, `domain:`/`difficulty:`/`split:` and `source:` tags).

## New: run protocols and metamorphic cases

- **`eval-protocol.yaml` and `weave eval --protocol <name>`** write the run protocol down (a commit run, nightly, a release gate, a weekly drift check) as named sets of `weave eval` options; the command line wins over the file, the report names the protocol, and a wrong file is refused by name.
- **`weave metamorphic`** derives, with no model, the cases that test a relation between two runs (an irrelevant addition, a reordering) and writes them beside the originals in a new folder; the report names a case that passes alone and fails perturbed.

- **Extractors ask for schema-constrained JSON where the provider can.** On OpenAI (gpt-4o and later, o1/o3/o4) and xAI (Grok 4 family), on chat completions and the Responses API, on Claude, on Gemini 2.5 and later, on Perplexity's Agent API and on a local Ollama server, an `extract` now sends its fields as a strict JSON Schema, so the reply is JSON by construction; elsewhere nothing changes. ## New: injection testing, routing matrix, handoff probe, `--emit-test`, judge biases

- **`weave security generate`** turns a corpus of injection payloads into a dataset (your own realistic artefacts with the payload embedded, a canary, the actions that must never happen). The report separates the model's obedience (a percentage, a mitigation) from the controls (a forbidden action fails the run).

- **`weave eval --emit-test <file>`** writes the opt-in JUnit class (free wiring test; real evaluation only with `-Deval.real=true`, capped); **`WeaveCLI.run(String...)`** is the public in-process entry it uses.
- **`weave judge validate`** also refuses a judge from the system's own model family (`--system-model`) and names a verbosity bias when the reference rows carry the output text. **`weave gate --protocol <name>`** runs the gate's eval stage as a protocol.

- **Review follow-ups (Phase 19 and 22):** `weave judge validate` is not usable for gating unless both `--model` and `--system-model` are named (a check that was not made does not pass), and model families are matched by vendor naming. A security summary says "not judged" instead of "controls held" when a mock run or an error judged nothing. `weave fabric up` treats only `localhost` and IP literals as this computer (a host name that starts `127.` is not), and `weave fabric status` takes `--bind`. `weave eval --emit-test` refuses a class or package name that is not a Java name. A committed template URL whose password is a `$VARIABLE` reference is not flagged.
- **Phase 19 gaps closed.** `weave metamorphic` also derives `paraphrase` (from `--paraphrases`, tagged `source:synthetic`), `monotonicity` (remove the evidence marked `decisive:<text>`) and `negation` (flip it with `negate:<from>=><to>`); the last two forbid the original conclusion. `weave judge validate --swapped <file>` checks that a pairwise judge's verdict does not follow the position (`--min-pairs`, default 10); a biased judge may not gate. `weave probe eviction` runs the real context manager on a small window with no model and checks that the oldest material goes first, the task stays and the model is told.
- **A Loom tutorial and a starter set.** [`docs/tutorial`](tutorial/README.md) teaches the language in fourteen chapters with 24 diagrams, from a first workflow to production, plain Java included. [`src/loom/starters`](../src/loom/starters/README.md) holds fifteen small workflows, each with a README, a picture drawn by `weave graph`, and tests that need no key. `StartersTest` and `TutorialExamplesTest` run on every build: every `loom` block loads without warnings, the Java examples compile, every link and heading anchor resolves, and a starter's README shows its real script and its real graph. `weave guide tutorial` writes the tutorial as one web page (`loom-tutorial.html`, with its diagrams) from inside the jar, so it is there without the repository; the page is generated from the markdown (`scripts/make-tutorial-html.sh`) and a test fails when it is out of date. `weave check` no longer warns that a variable is "also written as an ordinary word" in a script that says `substitution: braces`, where it is not.
- **`weave serve` no longer cuts its last reply short.** On `loom/shutdown` (and after a bad frame) the server waited until the reply left the queue, not until it was written, so a slow client or runner could receive half of it. It now waits for the write to finish.
