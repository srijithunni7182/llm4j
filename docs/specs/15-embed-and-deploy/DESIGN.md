# Phase 15 design: embed and deploy (typed bindings, `@LoomWorkflows`, `weave deploy`)

Status: **draft for review**. Layer: Loom (`ai-agent4j-loom`: packages `bind`, `deploy`; commands `weave bindgen`, `weave deploy`), the Spring Boot starter (`llm4j-spring-boot-starter`), an optional Maven plugin. Companion documents:
[TEST_STRATEGY.md](TEST_STRATEGY.md), [VERIFICATION.md](VERIFICATION.md), [program overview](../LOOM_DX.md). Builds on `LoomHost` (`RunRequest`, `RunOutcome`: `Completed | Suspended | Stopped`, `LoomRunFailedException`), the starter's `LoomRuntime` / `Llm4jLoomAutoConfiguration` / `HostRunner`,
`weave package --fat`, `EnvExampleCheck` and `weave check`'s credential listing, `--observe-fabric`, `weave audit`/[`weave review`](../09-review-engine/DESIGN.md), and the `llm4j-loom-deployer` skill.

## 1. Problem

Two seams stay manual after the workflow itself is good.

**Calling it from Java.** The embedding API is clean but stringly typed:

```java
RunOutcome out = host.run(RunRequest.of("Support", Map.of("ticket", text)));      // workflow name: a string; inputs: Map<String,String>
if (out instanceof RunOutcome.Completed c) { Object team = c.variables().get("team"); /* a cast, a key typo, no help from the compiler */ }
```

A rename of a workflow or a result field is a runtime failure in production. Every team writes the same wrapper: a facade, a record for the result, a mapper from the `variables` map, handling of `Suspended`/`Stopped`/`LoomRunFailedException`. Loom is a total language with declared signatures, `return { ... }` shapes, `output_schema`s and classifier answers,
so the compiler could do this for them.

**Running it for real.** `weave package --fat` produces a JAR. Putting that JAR on a server with Fabric attached, the right environment variables, volumes for journals, health checks and a safe network posture is the job of the `llm4j-loom-deployer` skill (which teaches a coding agent to do it step by step) and of each team's own Dockerfile. It is the same file every time.

## 2. Goals and non-goals

Goals:

- **Typed Java bindings** generated from the script: a facade interface per script, a record per workflow input and result shape, an outcome type that makes pause/resume explicit, compile-time-checked names.
- **Spring**: an annotated interface becomes a bean (`@LoomWorkflows`), with the host built by the existing auto-configuration; no hand-written wrapper.
- **Build integration**: bindings generated by `weave bindgen`, by a Maven plugin goal in `generate-sources`, and *verified* in CI so they cannot drift from the script.
- **`weave deploy`**: generate a container image recipe, a compose file (workflow + Fabric), a Kubernetes manifest set, and an environment template from the script, with the phase 9 review as a pre-flight and secrets never in an image.
- **Safe by default**: non-root container, read-only root filesystem where possible, journals on a volume, Fabric on an internal network, no ports published beyond what is needed, the lethal trifecta check and explicit acceptance carried into the deployment.

Non-goals:

- Not a new embedding runtime: `LoomHost` stays the engine; bindings are a typed *skin* generated over it.
- Not a language change beyond one optional, backward-compatible extension (typed workflow parameters, §3.3).
- Not cloud-provider-specific deployment, image registries, CI/CD pipelines for the user's app or cluster operations. `weave deploy` writes files; it does not run `docker push` or `kubectl apply`.
- Not generating tool implementations or Spring application code beyond the facade.

## 3. Typed bindings

### 3.1 What is generated

Given `triage.loom` with `workflow Main(message) { ... return { team: "...", route: "...", reply: "{reply}" } }`:

```java
// generated: com/acme/triage/TriageWorkflows.java   (do not edit; regenerate with weave bindgen)
public interface TriageWorkflows {

    /** workflow Main (triage.loom:33) */
    Outcome<MainResult> main(String message);

    // the same, with options (run id, label, origin, invoker credentials), as a builder:
    MainCall main();          // .message("…").runId("t-1").label("ticket 1").invoker(creds).start() / .run()

    static TriageWorkflows of(LoomHost host) { return new TriageWorkflowsImpl(host); }

    record MainResult(String team, String route, @Nullable String reply) {}   // reply is absent on some branches
}

public sealed interface Outcome<T> {
    record Done<T>(String runId, T value) implements Outcome<T> {}
    record Waiting<T>(String runId, Reason reason, Instant resumeAt, String stepId, String prompt) implements Outcome<T> {}   // suspended; holds no thread
    record Stopped<T>(String runId, String detail) implements Outcome<T> {}
    T orElseThrow();                                  // Done → value; otherwise IllegalStateException with the reason
    // resume/answer helpers on the facade: TriageWorkflows.answer(runId, stepId, "yes", "asha"); resume(runId) → Outcome<T>
}
```

- **R1** One generated file per script (plus its result records), in the package given by `--package`, deterministic (same script → byte-identical output; no timestamps, stable member order), with a header stating the source script, hash and generator version, and "do not edit".
- **R2** **Workflow names, parameters and results are compile-time names.** Renaming a workflow or a returned field in the script and regenerating makes the Java code that used it fail to compile — the point of the exercise.
- **R3** **Result shape inference.** For `return { f: ..., g: ... }` the record has fields `f`, `g`. When a workflow has several `return` statements with different shapes, the record has the union of fields; a field absent on some paths is nullable/`Optional` and documented with the paths that set it (from the graph). A workflow with no `return` yields `Void`-like `Outcome<Unit>` plus `variables()` access for the final context.
- **R4** **Field types** come from what is knowable: string interpolations → `String`; a variable bound from an agent with `output_schema` → a nested record or enum; from `intentclassify` → an enum per choice question plus `unsure`, `yes/no` as an enum, `rate` as an enum; a `run` task result → the task's declared result type when it has one; unknown → `String` (never `Object`), with a javadoc note. Enums include `UNSURE` where the runtime can produce it.
- **R5** **Inputs.** The runtime's inputs are strings (`RunRequest.inputs`: `Map<String,String>`). Untyped parameters become `String`. With typed parameters (§3.3) the facade accepts the Java type and serialises it with the documented rules (numbers, booleans, ISO dates, JSON for structured values), and the runtime parses it back.
- **R6** **Outcome handling is explicit and total.** The sealed `Outcome` mirrors `RunOutcome`; a failure is not an outcome, it is `LoomRunFailedException` as today (documented, unchanged). A `switch` over `Outcome` is exhaustive at compile time.
- **R7** **Variable access escape hatch.** `Done` offers `variables()` (the raw final context map) so nothing the script computes is unreachable, but typed access is the default.
- **R8** Generation is a pure function of the script and its import closure; it never loads user classes, calls a model or reads a secret. It reuses the `weave serve` symbol index (phase 10) / the validator's types, so it agrees with `weave check` by construction.
- **R9** If a script does not pass `weave check`, `bindgen` fails with the check's diagnostics (no partial output). If a result shape cannot be determined for a workflow, it generates `Map<String,Object> variables()` access for that workflow and says so in the build output, rather than guessing a type.

### 3.2 Commands and build

```
weave bindgen <script.loom> --package com.acme.triage [--out src/main/java] [--facade TriageWorkflows] [--nullability jspecify|none] [--check]
```

- **R10** `--check` regenerates in memory and exits 1 if the files on disk differ — the CI guard against a script changed without regenerating (also usable in a pre-commit hook).
- **R11** **Maven plugin** `io.github.srijithunni7182:loom-maven-plugin`, goal `bindgen` bound to `generate-sources`, configured with scripts and packages; adds the output directory as a source root; fails the build on `--check` semantics when `failOnDrift` is set. (Gradle: documented as an exec task; a plugin is a follow-up.)
- **R12** Generated code targets Java 17 (the project's baseline), has no dependency other than `ai-agent4j-loom` (for `LoomHost`) and optionally a nullability annotation module selected by `--nullability`, and compiles without warnings under `-Xlint:all`.

### 3.3 Optional typed parameters (language change, backward compatible)

`workflow Main(message: string, priority: number = 3, tags: list<string>)` — types are **optional**; `workflow Main(message)` keeps meaning "a string". Types: `string`, `number`, `bool`, `list<T>`, `object` (with `{...}` shape), `enum[A,B]`.

- **R13** Parsing: the old form parses unchanged, with the same AST meaning; a test pins the entire existing corpus parses identically. The new syntax is rejected cleanly by older versions with a `weave check` message (forward compatibility is a non-goal; the feature appears in a minor version).
- **R14** The runtime validates inputs against declared types when the workflow starts and fails fast with a typed error naming the parameter (instead of failing deep in a step on a wrong value); `weave test` cases and `weave run -i` use the same validation; `weave check` verifies call sites (`call Sub(x = ...)`) against the declared types where statically knowable.
- **R15** Defaults (`= 3`) apply when an input is absent. Parameters without defaults are required, and `weave check` already knows about unused/missing inputs.
- **R16** **Open question (§11.1):** whether to ship this language change in this phase or generate `String` parameters now and add types later. The binding design works either way; the spec describes both so the decision is explicit.

## 4. Spring: workflows as beans

```java
@LoomWorkflows(script = "classpath:triage/main.loom")           // or a bindgen-generated facade
public interface Triage {
    Outcome<MainResult> main(String message);
}

@Service class TicketService {
    private final Triage triage;                                // injected; a proxy over the starter's LoomRuntime
    Reply handle(String text) {
        return switch (triage.main(text)) {
            case Done<MainResult> d -> reply(d.value());
            case Waiting<MainResult> w -> park(w.runId(), w.prompt());
            case Stopped<MainResult> s -> retryLater(s.runId());
        };
    }
}
```

- **R17** `@LoomWorkflows` on an interface registers a bean implementing it (the bindgen-generated implementation when present, else a runtime proxy over the same logic). The starter's existing properties (`llm4j.loom.*`: persistence, executors, observe, secrets) configure the host; the annotation adds only the script location and the facade type.
- **R18** **Compile-time safety first:** the recommended path is bindgen-generated facades (names checked by the compiler). The runtime-proxy form checks interface methods against the script at **startup** (fail fast with a message naming the method and the nearest workflow), so a mismatch never survives the application's boot.
- **R19** Resume/answer are available as injected collaborators (`WorkflowRuns`: `answer(runId, stepId, text, by)`, `resume(runId)`, `status(runId)`), and `HumanQuestionEvent` (already in the starter) continues to announce pending questions.
- **R20** Test slice: `@LoomTest` (a Spring test annotation) swaps models/tools/humans for the phase 11 scripted collaborators so an application's integration tests run workflows with no model and no keys, while the rest of the context is real.
- **R21** Behaviour is **opt-in**: an application that does not use the annotation sees no change; auto-configuration conditions are covered by the starter's existing condition tests.

## 5. `weave deploy`

```
weave deploy <script.loom> --target docker|compose|k8s [options]
  --out <dir>                 where to write (default: ./deploy)
  --name <app>                image/app name (default: from the workflow)
  --base-image <ref>          default: a pinned JRE image (digest recorded)
  --with-fabric               include a Fabric server and wire the app to it (--observe-fabric), default for compose/k8s
  --fabric-image <ref>
  --journal volume|jdbc:<url>|none     where runs persist (default: volume)
  --env-file-template         write .env.example (names only)
  --expose none|http:<port>   whether the app listens (default: none: it is a worker)
  --schedule keep|none        keep Loom's own schedules (the app runs weave daemon) or run once per start
  --require-clean             exit 1 when open review findings remain (opt-in; by default deploy warns and carries on, R25)
  --dry-run                   print the file list and contents, write nothing
```

### 5.1 What is generated (R22 to R30)

| Target | Files |
|---|---|
| `docker` | `Dockerfile` (multi-stage: `weave package --fat` in the build stage → JRE image), `.dockerignore`, `entrypoint.sh` (runs `weave daemon`/`run` with the right flags), `.env.example`, `HEALTHCHECK` using a `weave` status call, `README.md` |
| `compose` | the above + `compose.yaml` (app + Fabric + a volume for journals and triggers), network `internal` for Fabric↔app, only the Fabric UI port optionally published on `127.0.0.1`, healthchecks, restart policy, resource limits, `secrets:` stanzas for keys (file-backed) |
| `k8s` | `Deployment`, `Service` (Fabric), `ConfigMap`, `Secret` *templates* (empty values), `PersistentVolumeClaim`, `NetworkPolicy` (egress only to the model providers named by the script + Fabric), `ServiceAccount` with no extra rights, `securityContext` (non-root, read-only root filesystem, drop all capabilities, seccomp runtime default), probes |

- **R22** Everything is derived from the script: the **environment variable names** from `env.NAME` uses (the `weave check` credential list), the **egress allow-list** from the providers/tools the script uses (`weave audit`'s data-flow list), the **volumes** from the journal/triggers/knowledge/memory settings, the **schedules** from `schedule` statements.
- **R23** **No secret in an image, a compose file or a manifest.** Values never appear; only names. Keys come from environment, files mounted from a secret store, or Kubernetes `Secret` references the operator fills. A test seeds secret-shaped values in the environment and greps every generated file. `.env.example` follows the existing `EnvExampleCheck` rule (placeholders only).
- **R24** **Reproducible.** The same script and options produce byte-identical files (stable ordering, no timestamps); base images are referenced by tag *and* digest when `--base-image` carries one, and the output says when it does not ("pin this before production").
- **R25** **Review notice, never a gate.** `deploy` runs the review (cached) and prints the summary and, as for every starting command (phase 9 R50), one warning line when findings are open; **generation always continues and the exit code is 0** (phase 9 R49). An open HIGH finding, including an unaccepted lethal trifecta, is stated in plain words in that warning and in the generated README, which lists the review summary it was generated under and any `trifecta: accepted "reason"` that was carried through. A team that wants a gate passes `--require-clean` (exit 1 when findings at or above the review's `fail-on` remain) or uses `weave gate`. The one thing `deploy` still refuses is the unsafe Fabric bind of R26: that is a configuration safety rule about exposing Fabric without access control, not a review finding, and is unchanged.
- **R26** **Network posture.** Fabric is not exposed beyond localhost/cluster-internal by default; if `--expose http` is requested the generated config includes the bind address and a note that Fabric access control must be configured (links to the deployer guide), and `deploy` refuses an unsafe bind exactly as the deployer scripts do today.
- **R27** **Observability wired.** The app starts with `--observe-fabric <url>` and the key via file/env; the compose file includes the Fabric `healthcheck` and the app `depends_on` it; the k8s manifests include the same.
- **R28** **State.** Journals/trigger stores on a volume (or JDBC) so a restart resumes runs; the generated README explains the three failure cases (restart, node loss, volume loss) and what each does to in-flight runs.
- **R29** **Idempotent and non-destructive:** `deploy` writes only inside `--out`, never overwrites a hand-edited file without a diff and confirmation, and records the generation hash in each file's header so edited files are detected.
- **R30** `weave deploy --verify <dir>` re-derives the expected files from the script and reports drift (a manifest edited by hand is fine; a stale env-var list is flagged), usable in CI.

### 5.2 Relationship to the deployer skill

- **R31** The `llm4j-loom-deployer` skill is updated so a coding agent *uses* `weave deploy` (and, like the other skills, reports open review findings in a sentence and carries on with the deployment the user asked for: phase 9 R56) to produce the files and then teaches the developer to read them; the skill keeps owning the *decisions* (security acceptance, `.inspect` rules, who may sign in) and the guidance on operating Fabric. The existing bundled scripts (`fabric-up`, `run-observed`, ...) remain for the non-container path. The skill's drift test (`SkillDriftTest`) covers the new commands.

## 6. Architecture

```
bind/       SchemaInfer (result shapes, types), JavaModel (records, enums, facade), JavaWriter, Naming, DriftCheck
            BindgenCommand
spring/     LoomWorkflows (annotation), LoomWorkflowsRegistrar, WorkflowProxy, WorkflowRuns, LoomTest slice
maven/      loom-maven-plugin (bindgen goal)
deploy/     DeployPlan (derived facts: env names, egress, volumes, schedules), Renderers (Dockerfile, compose, k8s), Preflight, Verify
            DeployCommand
```

- **R32** `bind/` and `deploy/` read the script through the same validator/graph/symbols code as `check`, `review` and `serve`; neither has a parser of its own.
- **R33** `deploy/` has no Docker, Kubernetes or network dependency; it renders text. Optional validation of the output (`docker compose config`, `kubectl --dry-run=client`) is a documented manual check, not a build dependency.

## 8. Decisions to confirm (open questions)

1. **Typed workflow parameters** (§3.3): ship in this phase (cleaner bindings, earlier errors) or later (bindings use `String`). Recommendation: ship, as optional syntax with the old form unchanged.
2. **Result shape = union of returns** (R3). Alternative: require all `return`s in a workflow to have the same shape, enforced by `weave check`. Recommendation: union with nullable fields now; offer a review rule (`LR11`) that suggests aligning shapes.
3. **Generated nullability.** `@Nullable` from JSpecify vs `Optional<T>`. Recommendation: `--nullability jspecify` default (records with nullable components), `Optional` available by flag.
4. **Maven coordinates and module.** A new `loom-maven-plugin` module vs adding the goal to an existing module. Recommendation: a new small module; confirm it fits the release process (`docs/PUBLISHING.md`).
5. **Which orchestrators.** compose and k8s plain manifests only (no Helm/Kustomize) in this phase; a Helm chart as a follow-up if requested. Confirm.
6. **Base image.** A pinned Temurin JRE 17/21 slim image. Confirm the choice and the policy for pinning digests.
