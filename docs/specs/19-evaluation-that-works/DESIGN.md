# Phase 19 design: evaluation that works (one command to a trustworthy per-agent report)

Status: **draft for review**. Layer: eval4j, eval4j-report, Loom (`weave eval`, `weave gate`, `weave test`), the dashboard. Part of the [field findings program](../FIELD_FINDINGS.md); read its §2, and decisions D8, D12 and D13 in §5, first.
Documents: [TEST_STRATEGY.md](TEST_STRATEGY.md), [VERIFICATION.md](VERIFICATION.md). Builds on [Phase 11](../11-workflow-tests/DESIGN.md) (`weave test`), [Phase 14](../14-production-loop/DESIGN.md) (`capture`, `regress`, `gate`) and [Phase 17](../17-honest-results/DESIGN.md) R5 (the output contract).
Findings owned: **F20 to F26** (the field session) and **F55 to F65** (capability gaps found by comparing the stack with the owner's QA guide). The skill that teaches the method is [Phase 23](../23-eval-design-skill/DESIGN.md).

## 1. Problem

Two different problems arrive in one phase, and it helps to keep them apart.

**A. The path that exists is hard to use and shows too little (F20 to F26).** In the field session, `weave eval` produced a judge verdict on empty text and an HTML report with no outputs, no per-agent view and no per-dimension scores. The good dashboard exists, and eval4j can fill it, but only through a JUnit class whose recipe is not in the guide: tags, `breakdowns: [agent]`, `declareAgent`, `declareJudge`, `bindTest`, `EvalRecorder`.
It took four attempts to get one real per-agent report. The judge's cost was missing from the cost, a rubric line could not belong to a dimension of its own, and one judge sample per line was read as a measurement.

**B. The method has needs the stack may not meet (F55 to F65).** The owner's QA guide says how to evaluate agent systems honestly: a pass rate instead of pass/fail, four kinds of oracle in order of preference, datasets that include the cases nobody builds, a split the tuner cannot see, a judge that is validated against humans before it gates anything, and results read with their uncertainty. Each of those needs something from the tooling: a split, an agreement score, an equivalence class, a repeated run, a version stamp. Which of them exist today is **not yet known** (a first grep over-counted; the real inventory is [VERIFICATION §0](VERIFICATION.md)).

The aim: **one command to a report a person can trust, with the numbers that tell them how far to trust it.**

## 2. Goals and non-goals

Goals:

- `weave eval` writes the same bundle the dashboard reads, and a first real run gives a per-agent, per-dimension report with outputs and reasoning (Part A, R1 to R7).
- The method's guards exist where they are cheap to provide and costly to forget: splits with a sealed held-out set, a validated judge, equivalence classes, repeated runs, version stamps, run protocols (Part B).
- Every number a report shows says what it rests on: how many runs, how many cases per slice, which dataset and configuration, whether the judge was validated, and what change the instrument could not detect.

Non-goals:

- Not a new evaluation framework. eval4j stays the engine and the dashboard stays the viewer; this phase connects `weave eval` to them and adds what is missing.
- Not a Python or pytest port of the guide's harness. The guide's method is language-neutral; its code is translated by [Phase 23](../23-eval-design-skill/DESIGN.md) (D13).
- Not hosted tracing or a monitoring platform.
- Not automatic ground truth: no feature writes the answer key from a model. A synthetic case says it is synthetic.
- Not the skill's process, the preflight, or the editor's display of results (Phases 20, 23, 21).

## 3. Part A: make the path that exists usable

**R1 `weave eval` writes the eval4j bundle (D8).** A run writes the folder the dashboard reads (`target/eval4j/…` for Maven projects, `<project>/eval-runs/<id>/` for script-only ones): the cases with their **outputs**, the verdict of every rubric line **with the judge's reasoning**, dimensions, the `agent:` tag, tokens and cost for the agents and for the judge, the configuration fingerprint (model, prompt and workflow versions, judge model and prompt version, dataset version, commit) and the run's own settings (repetitions, split, protocol). The old HTML report is produced **from** that bundle, so there is one source of truth. `weave eval --open` opens the dashboard.
**R2 Outputs are kept** in the bundle and shown in the case drawer ([Phase 17 R5.5](../17-honest-results/DESIGN.md)); an empty output is an error case, never a judged one.
**R3 A rubric line can name its dimension (F22).** In a dataset, `rubric:` accepts plain strings (as today) and objects `{ text: "…", dimension: grounding }`. A line with a dimension is filed under that dimension **only**. A plain line keeps today's behaviour (filed under every dimension of the case) and `weave eval --check` says so once per case ("3 lines are counted under every dimension; give each a `dimension:` to count them once").
**R4 The agent view is always there (F20; owner's priority, 2026-10-29).** A report **always** has the "By agent" table, with no tag, flag or configuration. The agent of each result is **taken from the run itself** (the trace says which agent produced which step and its tokens, cost and finish reason), and an `agent:` tag on a case only adds the case's *expected* agent. Per agent the table shows: cases and runs, pass rate with its interval, quality by dimension, the agent's own cost and tokens, answers cut at a limit (Phase 17 R2.3), fallbacks taken (R4.1 there), the worst three outputs with the judge's reasoning, and a link to each. Where a result cannot be tied to an agent (for example a workflow that returns one text), the table says so with the reason and offers the step-level fix, instead of being left out. `weave eval --init` still writes `eval4j-report.yaml` (dimension goals); the recipe, with the `declareAgent`/`declareJudge` calls for Java users, is a section of the eval4j user guide and the Loom guide, tested by a docs test that runs the sample. Whether the trace already carries the agent per step is a question for [VERIFICATION §0](VERIFICATION.md) (P2); if not, adding it is part of this requirement.
**R4.1 The report contract.** The report's structure is fixed and **tested as a structure**, so it cannot quietly lose a part. Every report, from every command that writes one (`weave eval`, `weave gate`, the generated JUnit class), has these sections in this order: (1) **Read this first** (§5); (2) **Overall**: quality, cost, the run's settings and fingerprint; (3) **By agent** (R4); (4) **By dimension**; (5) **By slice** (split, difficulty, class, with the small-slice warning); (6) **Cases**: every case with its output, every rubric line's verdict and reasoning, tokens and cost; (7) **Cost**: agents, judge, total, per success; (8) **Cautions**: every warning the run raised (unmatched rate, unstable lines, no held-out set, estimated usage, fallbacks), none hidden; (9) **How to reproduce**: the exact command and the bundle's location. A section with nothing to show is **still present** and says why ("no held-out cases: see R9") rather than disappearing. The HTML, the JSON bundle and the terminal summary carry the same sections from the same data, and a golden-structure test per fixture fails when a section, a column of the By-agent table or a field of a case is missing or reordered.
**R5 A generator for projects that want the Java API (F21, D8c).** `weave eval --emit-test` writes the opt-in JUnit class (off unless `-Deval.real=true`; a spend cap; the registrations the recipe needs) for a project. It compiles and runs in a hermetic mode in the tests of this phase.
**R6 The judge's cost is part of the run's cost (F24).** The run summary and the dashboard show **agents**, **judge** and **total** separately; `--max-cost` bounds the total; the cost line says measured or estimated ([Phase 17 R6](../17-honest-results/DESIGN.md)).
**R7 Judge samples (F23).** `--judge-samples N` scores each rubric line N times and reports the **median and the spread**; the default is 1 in a development run and 3 in a release run (the protocols of R14). A line whose samples disagree by two points or more is marked unstable and is not counted toward a gate.

## 4. Part B: what the method needs

Each requirement below is **conditional**: [VERIFICATION §0](VERIFICATION.md) inventories what exists. A requirement that is already met is recorded as met and dropped; a partly met one is narrowed. Priorities: **T1** the report is misleading without it; **T2** the method is hard to follow without it; **T3** valuable, can follow.

**R8 (T1) Dataset version and baselines that cannot slide (F62).** `dataset.yaml` has a `version`, bumped on any case change and recorded in every run. A comparison across versions is **refused** unless `--allow-version-change "<reason>"` is given (the reason is recorded). A baseline is saved with a **named approver and a written rationale** (`weave eval baseline save --approver … --why …`); a comparison reports against the current **and the previous** baseline, so a slow decline across releases shows. Re-baselining is never automatic.
**R9 (T1) Splits and a sealed held-out set (F55, D12).** A case has `split: development | validation | heldout` (default `development`). `--split` selects; the report slices by split. **Held-out cases run only with `--release-gate`** (the guard of D12b; the run records that it was a gate run and who asked, and the cases' text is not printed in a development report); the **generalisation gap** (validation minus held-out) is reported beside quality, and a gap over 10 points prints "the dataset may be fitted; refresh it". `weave eval --check` warns when a project has no held-out cases. Whether the person who owns the dataset also owns the prompts cannot be checked by a tool, so the report footer says it as a reminder: the party being measured should not control the measuring instrument.
**R10 (T1) The verdict set, and the unmatched rate (F57).** A case may state `correct_conclusion`, `accepted_equivalents`, `rejected`, `acceptable_actions`, `unacceptable_actions` and `required_citations`. The outcome verdict is `exact | acceptable | rejected | unmatched`. Matching prefers, in order: **structured output** (the agent emits a code and the script compares), an **embedding** similarity above a threshold tuned on a calibration set (optional), an **LLM comparison** as a last resort (flagged in the report as adding non-determinism to the oracle). Unmatched outputs go to a **human review file** (`unmatched.yaml`: the case, the output, a line for "accept as equivalent" that, when filled in and merged, adds an `accepted_equivalents` entry and bumps the case's version). The report warns above **10% unmatched** ("the ground truth is incomplete, so every other number is suspect") and says "add accepted equivalents rather than loosening the threshold".
**R11 (T1) Consistency and resolution (F60).** `--repetitions N` runs each case N times. The report gives **pass@1** and **pass^N** side by side, **consistency@N**, the **unstable cases** (pass rate between 0.4 and 0.6; "usually under-specified, send to the dataset owner"), Wilson confidence intervals, slices by difficulty and by split, and a plain **resolution statement**: "this run (120 cases × 5) can detect about a 10-point change; a smaller change is below its resolution". The significance test of an existing comparison is reused.
**R12 (T2) Judge validation (F56).** `weave eval judge validate --reference <file>`: a reference set of at least 40 outputs scored independently by up to three humans on the same rubric. It computes **inter-human agreement first** (quadratic-weighted Cohen's kappa; below 0.6 the **rubric** is under-specified and the command stops), then **judge against the human consensus** (kappa, mean bias, the cases where the judge is two or more points away), and prints the reading table (below 0.4 poor, 0.4 to 0.6 not good enough for gating, 0.6 to 0.8 usable, above 0.8 strong). The result is stored with the judge's identity (model, prompt version, rubric version). **`weave gate` can require it** (`--require-validated-judge`): a dimension whose judge has no passing validation does not gate. An **audit sampler** (`weave eval judge audit --sample 5%`) picks judged runs for human scoring and tracks judge-human agreement over time. The known judge biases (verbosity, position, self-preference, sycophancy, anchoring) are listed in the report footer with what the configuration did about each: the judge runs at temperature 0, scores one dimension per call, uses a different model family than the agents (a warning, not a block, when it does not), and randomises order in comparisons.
**R13 (T2) Cost per success and its tail (F61).** The report shows **cost per successful task** (total cost divided by passing runs), median and **p95** cost, the **runaway rate** (runs that hit a hard bound) and the **graceful-termination rate** (bound hits that kept partial work). Quality and cost sit on the same page, because separately they get optimised against each other.
**R14 (T2) Run protocols (F64).** A project declares named protocols in `eval-protocol.yaml`: for example `commit` (a core subset of about 20 cases, 3 repetitions), `nightly` (the validation set, 5), `release` (validation plus held-out, 10, `--release-gate`), `drift` (the validation set, 5, **the configuration pinned, run on a schedule whatever changed**). `weave eval --protocol nightly` runs one; `weave gate` takes a protocol; the docs give a scheduled GitHub Actions workflow for `drift` (the only mechanism that catches a provider's silent change).
**R15 (T3) Case classes and slice sanity (F59).** A case's `class` may be `unanswerable`, `obvious-wrong` or `conservative-action`; `weave eval --check` reports each class's share and warns below **10%**, warns on any reported slice (domain, difficulty, split) with fewer than **10 cases**, and reports the composition by `source` (`production`, `expert`, `synthetic`; the guide's 50, 30, 20) as information, not a rule.
**R16 (T3) Metamorphic cases (F58).** `weave eval metamorphic --from <dataset> --relations paraphrase,irrelevant,order,negation` derives cases that assert **a relation between two runs** (the conclusion class is the same under paraphrase, an irrelevant addition and re-ordered evidence; it **changes** when the decisive evidence is removed). Mechanical relations (order, irrelevant addition, removal) need no model; paraphrase uses a model and the case is marked `source: synthetic` with the generating model named.
**R17 (T3) A security corpus runner (F63).** `weave eval security --corpus <dir>` runs a versioned corpus of injection payloads (classes: direct, indirect; placements: documents, web pages, logs, file names, tickets, API fields, code; goals: override, approval spoofing, tool coercion, exfiltration, split payload, and so on) embedded in the project's **own realistic artefacts** (templates that put a payload where the workflow reads), and reports **the proportion that changed behaviour**. For **every payload that did**, it checks the **system-level controls** (a tool call with attacker-chosen arguments, an effect without its approval, an outbound send, a write outside the allowed folder) and reports "controls held: 100% / failed: …". The report says plainly that a 99% resistance rate means one crafted payload in a hundred succeeds, and that the controls, not the percentage, are the defence. A small starter corpus (every class and placement once) ships; the project's own successful attacks become cases ([Phase 14](../14-production-loop/DESIGN.md) `capture`).
**R18 (T3) Trajectory, routing and context probes (F65).** Where `weave test` does not already cover them: a **routing confusion matrix** over a labelled routing set (reported as a matrix; the dangerous cells, such as an information-gathering request sent to an action agent, gate on their own); a **handoff context probe** (plant a fact before a `handoff` and assert the receiving agent has it); **loop induction** (an `unhelpful` tool fault repeated; each bound fires independently and the work is preserved); a **context-eviction probe** on a small context window (eviction order defined, the model told, conclusions do not rest on evicted material); and **turn-level versus session-level** metrics for conversation datasets.

## 5. What a report must say

A report that follows R1 to R18 (and the structure of R4.1) opens with a **"Read this first"** strip: the run's configuration fingerprint and dataset version; the number of runs and cases and the **resolution** of the run; pass@1 and pass^N; the unmatched rate; the generalisation gap (when a held-out set was run); slices with fewer than 10 cases; the judge's validation status and its cost; and the cost per success. Every one of those is a number the owner's QA guide calls necessary for an honest reading, and every one is a line the dashboard did not have in the field session.

## 6. Compatibility

| Change | Existing datasets and reports |
|---|---|
| R1, R2 | The HTML report keeps its name and opens as before; the bundle is new. A project that never ran `weave eval` is unaffected. |
| R3 | Plain `rubric:` strings behave as today; only an object with `dimension` changes counting. |
| R8 | A dataset with no `version` gets `0` and a one-line note; nothing is refused until it has one. |
| R9 | Cases default to `development`; no held-out cases means no gate guard applies, and the check says so. |
| R10 | Existing `expected_output_contains` and rubric checks keep working; the verdict set is for cases that state the new fields. |
| R12 to R18 | New commands and options; nothing existing changes. |

## 7. Security and privacy

- A held-out case's text and a human reference score are data an attacker or a careless tuner could use: the report prints neither in a development run (R9, R12), and the bundle's held-out section is marked.
- The security corpus (R17) contains hostile text; it runs against fake or sandboxed tools by default (`weave eval security` refuses a workflow whose tools can reach the real network or filesystem unless `--allow-real-tools` is given and the audit has passed), and its output goes to the run's own folder.
- Reference scores name people only by the labels the project chooses; no identifiers are required.
- The judge never receives secrets: the existing masking rules apply to the output it is shown.

## 8. Open questions

1. R12: a project with no humans to score a reference set (a solo developer): is a **single-human** validation, with its limits stated, better than none? Proposed: allowed, labelled "single rater: agreement with a second human is unknown", and not enough to gate a release dimension.
2. R9: should `heldout` also be hidden from the **agent that tunes** (a coding agent)? The sealed-case guard cannot stop a tool that reads the file. Proposed: the dataset's held-out folder is outside the tuning project (an environment variable names it), documented as the way to keep it sealed.
3. R10: the embedding matcher needs an embedding provider; eval4j has one for RAG. Proposed: optional, off by default.
4. R17: how large must the starter corpus be before it is worth shipping? The guide says 60 or more direct and 100 or more indirect for a real programme; a starter of one per class and placement is a start, not a programme, and the report says so.
5. R14: where do scheduled drift runs write and who is told? Proposed: the bundle, and a non-zero exit that the CI's own alerting turns into a notice.
