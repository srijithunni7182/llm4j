# Phase 31 test strategy: prompt caching and multimodal input

How each requirement of [DESIGN.md](DESIGN.md) is tested. The rules of [TESTING_STRATEGY.md](../../TESTING_STRATEGY.md) apply: the default build is hermetic (no network, no real model, no wall-clock waits),
tests are written first, and a security guard is tested by breaking it on purpose.

## 1. Principles

- **The wire format is the contract.** Providers are tested with OkHttp `MockWebServer`: the test reads the request body the writer produced and asserts the exact JSON shape, then replies with a recorded response.
- **No media in the repository that could be mistaken for a secret or a payload.** Fixtures are tiny, generated bytes (a 1x1 PNG, a minimal PDF, a few bytes of WAV/MP4 header) built in the test, not binary files committed to the tree.
- **Refusal is a feature.** Every "we refuse" requirement has a test that shows the refusal and a test that shows no HTTP request was made.
- **Never the bytes.** One shared assertion, `assertNoPayloadLeak`, scans `toString`, Jackson output, log appender output, exception messages, journal lines and trace output for the base64 of the fixture.

## 2. Levels

| Level | What it covers |
|---|---|
| **Unit** | `Media` (sniffing, kind mismatch, unknown format, SVG refused, defensive copy, hash, `toString`), `MediaPolicy` (each limit at, below and above), `PromptCache` (breakpoint count), `MediaCapabilities` |
| **Contract** | `ProviderContract` gains two cases every chat provider must pass: text-only requests are byte-identical to before (golden bodies), and media the provider cannot take throws `InvalidRequestException` with no request sent |
| **Writer** | One test class per provider: media order, the text part, several items, base64 correctness (decode the body and compare to the fixture), absence of unrelated fields; Anthropic `cache_control` placement and the four-breakpoint limit |
| **Decorator** | `MaskingLLMClient`, `BudgetedLLMClient`, routing and retry pass media through unchanged; masking with media is refused per D7; a decorator that cannot handle media refuses |
| **Accounting** | Token estimates are conservative (never below the vendor's reported figure for the recorded responses) and replaced by reported usage; cache read and write are priced separately |
| **Loom parser** | `attach` after `to` and before `->`, several items, every statement that accepts it, the statements that must reject it (`note`, `halt`), error messages, and a script with an agent or variable named `attach`/`media` still parses |
| **Loom check** | Each R17 finding, with the position and the fix in the message |
| **Loom runtime** | End to end with a fake `LLMClient` that records the `LLMRequest`: the media arrives on the first user message; a missing file fails without retry; `on_failure` runs; resume reloads and checks the hash |
| **Security** | Path traversal (`..`, absolute, symlink out, a path built from a variable, a path from a model's output, case and encoding tricks), content-type confusion, oversize, decompression-style bombs (a tiny file that claims huge dimensions is bounded by bytes, not trusted), count limits |
| **Audit** | LA23 fires for media from a variable and not for a literal file; it completes the trifecta when the other legs are present; `SecurityDocTest` finds it listed |
| **Docs** | The `loom` blocks in `LOOM_GUIDE.md` parse (existing test), the new samples are checked with `weave check`, the VS Code grammar test finds the new keywords, `API_COMPATIBILITY` lists the new types |
| **CTK** | New Loom scenarios for attach, a refused kind and a refused path |
| **Mutation (PIT)** | A new profile covers `Media`, `MediaPolicy`, the source resolver and the capability check (the decision-making classes), at an 85% threshold |
| **Live (tagged `live`, never default)** | One call per provider that supports each kind, with the owner's keys, run only when asked: confirms the recorded fixtures still match the real APIs |

## 3. Fixtures

- **`TinyMedia`**: builds the smallest valid PNG, JPEG, GIF, WebP, PDF, WAV, MP3, MP4, WebM in memory, plus deliberately wrong ones (PDF bytes named `.png`, an SVG, truncated headers).
- **`RecordingClient`**: a hand-written `LLMClient` fake that keeps the last `LLMRequest`, used by the Loom runtime tests (no mocks of types we own).
- **Recorded responses** per provider, taken from the real API once (live) and checked in as text, like the Phase 8 and 30 fixtures. Request bodies are golden files with the base64 replaced by a placeholder.
- **`TempMediaRoot`**: a temporary directory with a root, a file outside it, and a symlink pointing out, built per test.

## 5. Test the guards themselves

Each of these is checked once by **removing the guard and watching a test fail**, and the result is written in [VERIFICATION §7](VERIFICATION.md): the content sniffing; the kind-versus-sniffed comparison; the SVG
exclusion; the per-item, per-message and per-request limits; the path containment; the symlink check; the capability check; the PII refusal; the hash check on replay; the payload-leak assertions.

## 6. What is deliberately not tested

- That a model reads an image **well** (that is evaluation, not this phase).
- The vendors' own size limits beyond the ones recorded in capability data; the live tests confirm those when run.
- URL sources, provider file stores, media output and realtime streams (non-goals).
