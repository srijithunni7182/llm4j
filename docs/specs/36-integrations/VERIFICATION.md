# Phase 36 verification plan: integrations

Status: **final for phase 36; nothing is built.** Section 0 lists what was read and what is still to read; section 1 lists what must be proved. Companions: [DESIGN.md](DESIGN.md), [TEST_STRATEGY.md](TEST_STRATEGY.md), [DECISIONS.md](DECISIONS.md), [phase 35 VERIFICATION](../35-framework-tools/VERIFICATION.md).
**Evidence levels:** E0 read in the source or documents; E1 a unit test; E2 an engine test with scripted models on the controlled scheduler; E3 a kill-and-resume or concurrency test; E4 run by hand on a real system (the owner's gate). **Integration** means an `@Tag("integration")` test that runs only where a network and a container runtime exist. No live model key is needed for the default build; `make test-live` is never run.

### Notes from the reads (written by the build; each says when it was read)

- **R15 (before 36a, 2026-11-14): phase 35 is on `main` as specified.** `ToolKind.profile` (core and Loom), `DiscoveredKinds` (`ServiceLoader` over `META-INF/services/io.github.llm4j.agent.tool.ToolKind`), the `sandbox`, `workspace`, `compute`, `verify` and `scan` kinds in `ai-agent4j-tools`, the four extras modules (`search`, `documents`, `git`, `browser` under `src/tools/extras`), `docs/TOOLS_CATALOG.md` and `src/tools/ai-agent4j-tools/docs/writing-a-tool.md` all exist. **One gap found and fixed:** `make setup` did not install `ai-agent4j-tools`, so on a fresh checkout Loom compiled against an older release jar in `~/.m2` and failed on the phase 35 kinds; `scripts/setup-dev.sh` now installs `src/tools` and `ai-agent4j-tools` too (commit `chore: make setup installs the tools module too`).
- **R18 (before 36a): the `substitution` setting is already gone on `main`.** `LoomParser` refuses a `substitution:` line with "delete this line"; `LOOM_GUIDE.md` and `docs/API_COMPATIBILITY.md` say only `{name}` is replaced in a text. No file written by this phase uses the word as a setting. How a `command` template stays out of that replacement is read in 36c.
- **R2 (36a, first): `swagger-parser` 2.1.19 fetches on its own, and it can be stopped.** A scratch program (loopback `HttpServer`, spec with an external `$ref` to it) showed: `readContents(spec, null, resolve=true)` fetched the `$ref` (one request, with `resolveFully` true or false); `readLocation("http://…")` fetched the spec itself; **`readContents` with `resolve=false` made no request at all.** The fetching goes through the parser's own `RemoteUrl` (a bare `URL` connection), so it bypasses `NetPolicy`; the jar `swagger-parser-safe-url-resolver` exists but is an allow-list of its own, not our policy. **Consequence, built as D2 and G70 say:** the new kind fetches a remote spec and each external `$ref` itself through `HttpSupport` and `NetPolicy`, inlines them, refuses a file `$ref` outside the spec's folder, and only then gives the parser a document with no external reference (`resolve=false` first, so a reference it missed fetches nothing). The old core `OpenAPIParser.parse` (`readLocation`, `resolve=true`, `resolveFully=true`) is the unguarded path being deprecated.
- **R3 (36a, first): MCP tools reach an agent without the approval and decision wrappers by any path.** In `HarnessExecutor` the `approve:` and `approve: all` wrapping (`ApprovalTool`) and the `EvidenceTool` wrapping run only inside `for (String toolName : agentDef.getTools())`; the `mcp_servers:` loop later calls `agentBuilder.addTool(new McpToolAdapter(...))` directly. `McpToolAdapter` does not override `Tool.requiresApproval`, which defaults to false, so the agent's `approvalCallback` never sees an MCP tool; and `approve:` names a declared tool, which an MCP tool is not. `PolicyToolHook` is added for an agent with an MCP server (its `mcp` flag), so policy hooks do reach them, but approval does not. **Confirmed gap, not a contradiction of D6:** D6 already says to wrap them; G79 pins it. A failed `tools/list` is `log.severe` and swallowed, as DESIGN said.
- **R1 (36a): `OpenAPITool.SUPPORTED_METHODS` is `GET, POST, PUT, DELETE`**, while `OpenAPIParser` also extracts PATCH: a PATCH operation is listed in the description and then refused at call time (`Unsupported HTTP method`). The new kind supports GET, HEAD, OPTIONS, POST, PUT, PATCH and DELETE (D4's table names all of them). `Capabilities.operationEffect(ToolDef, String operation, Capabilities)` is keyed by `operationId` and has no production caller; `ToolDef.getOperationEffects` is filled by the parser and read only by that method.
- **R6 (36a): `StdioMcpTransport`** builds a `ProcessBuilder` and puts the script's map on top of the whole inherited environment; `redirectError(INHERIT)`; the reader is a daemon thread that logs a parse failure and carries on; `close()` calls `destroy()` and does not wait or `destroyForcibly`; there is no liveness check, so a crashed server leaves the next request to wait out the 30-second `McpClient` timeout, a constant with no setting. `McpClient.callTool` returns the raw result and never reads `isError`; `listTools` ignores `nextCursor`; `initialize` offers `2024-11-05` and ignores the server's answer.
- **R7 (36a): a tools-module or extras kind cannot take `invoker.NAME` today.** `lateBound()` and the `create(name, options, sources, dir, context)` overload exist only on Loom's own `ToolKind`; the core `io.github.llm4j.agent.tool.ToolKind` that every extras kind implements has neither, and `GenericKindAdapter` forwards only the four-argument `create`. `openapi`'s `auth_value` works today only because Loom's own `OpenApiKind` is a Loom kind. **Consequence:** moving `openapi` to an extras module (D2) would lose `invoker.NAME` unless the core interface gains the two members. They are added as **default methods** (additive, nothing breaks), and `GenericKindAdapter` forwards them; `http` can then take `invoker.NAME` in 36b with no further plumbing.
- **R13 (36a): `ErrorCategory`** (core, public) has 17 values, including `AUTHENTICATION` (401/403 by status) and `PERMISSION_DENIED`; Loom's `Failures.CATEGORIES` is the closed list of seven. `CREDENTIAL_REJECTED` is added to the core enum as an additive value and `credential_rejected` to the Loom list (D16); it is distinct from `AUTHENTICATION`, which a bad *model* key also produces.
- **R8 (36a, partly):** `SecurityAudit` reads `a.getMcpServers()` (line 204) and the server list (line 858) and assumes all three legs for an MCP server; `McpEffects.resolve` has no production caller; the `mcp` block's `effects:` map is stored by `McpServerDef.putToolEffect` and read only by `McpEffects`. The wiring is built in 36a (see the build notes at the end of 36a's report).

- **R2, weight (36a):** `mvn dependency:tree -pl src/tools/extras/ai-agent4j-tools-openapi` now resolves. `swagger-parser` 2.1.19 brings about **forty transitive jars**, not only the thirteen under `io/swagger`: its Swagger 2 converter pulls `swagger-parser` 1.0.68 and `swagger-compat-spec-parser`, which bring `java-json-tools` (json-schema-validator, json-patch), **Rhino**, **Apache HttpClient 4.5.14**, **guava** (and its annotation jars), `joda-time`, `libphonenumber` and `jopt-simple`, plus `snakeyaml`, `commons-io`, `commons-lang3`, `jackson-dataformat-yaml` and `jackson-datatype-jsr310` (the last two at 2.15, beside the 2.23 `jackson-databind` the core uses). The direct jars alone are 940 KB on disk; D2 said the weight "is moderate and is not the reason", and that stands as a decision, but the real figure is larger than the 1.7 MB of 13 jars the design measured. The module's `WeightTest` pins its four direct dependencies. Apache HttpClient is on the path only for Swagger 2 specifications, which this module does not read (OpenAPI 3 only, through `readContents`).
- **R4 (36a): MCP clients live as long as the executor.** `HarnessExecutor` owns one `McpServers`, started in `initialize()` and stopped by `shutdown()` (it was never stopped before: nothing closed the clients). `LoomHost` builds **one executor per run** (`LoomHost.java`: `new HarnessExecutor(script, tools, models)`, and counts the ones it shuts down), so a host's servers are per run; `weave run`, a packaged app and a daemon build one executor and may run many workflows on it, so there the servers outlive a run. A stdio server carries no token, so nothing crosses runs today; the rule matters for 36b's HTTP transport.
- **R5 (36a, the annotations), from the schema page of the 2026-07-28 and 2025-11-25 revisions** (vendored under `src/mcp-testkit/src/main/resources/mcp/schema`, with hashes in `METADATA.json`): `ToolAnnotations` has `title`, `readOnlyHint` (default **false**), `destructiveHint` (default **true**, meaningful only when `readOnlyHint` is false), `idempotentHint` (default **false**, meaningful only when `readOnlyHint` is false) and `openWorldHint` (default **true**). The schema's own description says: "all properties in `ToolAnnotations` are hints ... Clients should never make tool use decisions based on `ToolAnnotations` received from untrusted servers." `McpEffects.propose` follows these defaults. In the 2026-07-28 schema `CallToolResult` also requires `resultType` and `ListToolsResult` requires `cacheScope`, `resultType` and `ttlMs`; `server/discover`, `DiscoverRequest`, `DiscoverResult` and `UnsupportedProtocolVersionError` exist there and not in 2025-11-25. The **2025-11-25** revision is the newest of the `initialize` era, so the client offers it. **Licence:** the specification repository says it is moving from MIT to Apache-2.0, with contributions licensed per author; both are compatible with this repository's Apache-2.0, and the licence file is vendored beside the schemas. **Not read yet:** the Streamable HTTP binding page and which revision each reference server implements (36b).
- **R8 (36a), the audit and MCP:** `SecurityAudit` assumed all three legs for every `mcp` server and listed it as unapproved outward unless `approve: all`; with `effects:` and `reach:` it now narrows the legs and lists a declared-changing tool as needing approval (`McpEffectsWiringTest`). The same facts reach `PolicyToolHook` (a declared read is not checked as a changing tool) and the run's own read classification (`ReadClass`). `weave review` and `whatif` read the same audit facts; no separate wiring was needed (the audit's `LA08` text, "give agents that use them `approve: all`", was untrue until this phase, because `approve: all` did not reach an MCP tool).
- **R12 (36a, in part):** `WeaveCLI` registers a command with `.addSubcommand(new …Command())`; the testable shape is a static method taking a `WeaveEnv` (out, err, a `HumanInterface` for the question, the environment and secret store), as `ToolsCommand` does; `weave mcp list` follows it. `Doctor` was not read yet (36e).
- **R13 (36a), done:** `ErrorCategory.CREDENTIAL_REJECTED` is added at the **end** of the enum (so no existing ordinal moves), `Outcome.Status.CREDENTIAL_REJECTED` likewise, and `credential_rejected` is a category a `fail:` can inject. **What is not built:** Loom has no `on_failure` branch by category (the categories reach tests' failure injection and the trace), so "a host's trace listener can tell it apart" is met by the audit event's `outcome: credential_rejected` and the typed exception, and nothing routes a rejected credential to a handler of its own yet.

### Where the code contradicts a decision or the design (filled in by the build)

Four findings, none stopped the build (each has a safe default that was built, and the owner can reverse it at the 36a gate). **Decisions the owner is asked to confirm or change:**

1. **A description's `servers` entry is untrusted, so an existing script that reaches a private, loopback or plain-http API named by its spec stops working until it adds `allow_private: true` (and `allow_http: true`) or `base_url:`.** D2 and G69 say the new kind sends every request through `NetPolicy`, and the task's security rules say a specification is untrusted input, so that is what was built. The compatibility rule (scripts written before this phase "must still load and run") and G92 read the other way for such a script: it *loads*, and then every call is refused with a message that names the fix. Seven existing Loom test scripts (the invoker tests, `ToolsTest`) were of this shape, and they now say `allow_http: true  allow_private: true`. **Question for the owner:** is a refusal with a clear message the intended migration, or should the older all-operations form (no `operation:`) keep reaching a private address the description names, with a warning, until the next major? Built: the refusal; recorded in `docs/API_COMPATIBILITY.md` under "Integrations (phase 36)".
2. **D14 says `weave audit --strict`; there is no such flag.** `--strict` exists on `weave check` (a warning becomes an error). LA35 is therefore raised by `weave check` (a warning, an error with `--strict`) and is listed with the audit rules (`AuditCatalog`, `docs/security/weave-audit.md`) with that said plainly, because the audit reads no files and a pin must be compared with one.
3. **D8 point 4 says `credential_rejected` lets `on_failure` and a host's trace listener tell the case apart.** Loom has no failure-category branch in `on_failure` (R13). What exists: the typed `CredentialRejected`, `Outcome.Status.CREDENTIAL_REJECTED`, the audit outcome, and the category in `fail:` for tests. Routing a rejected credential to a handler by category is a language change and was not made.
4. **D6 says MCP annotations remain "a proposal a person approves"; the existing `McpEffects` used `readOnlyHint: true` as an assumed `reads`.** The decision wins (and the schema page says clients should never decide from annotations of a server they do not trust): `McpEffects.resolve` no longer takes the annotation as an effect, `McpEffects.propose` carries the D4 table, and `McpHintsTest` was rewritten to say so. This changes what a script that relied on the (never-wired) hint sees: nothing, because no production code called it.

**Smaller things the build found, not decisions:** `make setup` did not install `ai-agent4j-tools` (fixed); the old OpenAPI tool did not percent-encode path values, refused PATCH after listing it, and cut every answer at 2,000 characters (all three changed, recorded in the ledger); `GenericKind` already refused a credential shorter than four characters, so an `openapi` `auth_value` now must be four or more; the audit's own `LA08` advice (`approve: all` for MCP) was not true until this phase; the stdio client logged every message body; MCP servers were never stopped.

## 2. How the report is written

At the end of each sub-phase the report states, for each row, the level reached and the evidence (the test names), **what was not run** (`make test-full`, the other `slow` tests, every integration test that needed a network or a container runtime the session lacked, anything at E4), the risks of DESIGN §4 that turned out to be real, each R-item read and what it found, and any decision that was changed and why. A row is never marked reached without the test that proves it. **If a session cannot start a container runtime or reach a real service, the integration tests and the differential runs are reported as not run, not as passing.**
